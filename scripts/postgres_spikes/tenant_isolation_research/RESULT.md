# Отчёт об исследовании изоляции тенантов в Apache AGE (Spike: Tenant Isolation)

## 1. Цель и контекст исследования

В рамках перехода Archon к модели Managed SaaS ([ADR-0006](../../../docs/adr/0006-saas-delivery-model-and-ai-native-source-of-truth.md)) и выбора графового движка для хранения архитектурного Source of Truth ([OQ-2](../../../docs/architecture/open-questions.md#oq-2), [OQ-5](../../../docs/architecture/open-questions.md#oq-5)) необходимо определить модель мультитенантности в PostgreSQL 16 + Apache AGE.

Ключевое требование к корпоративной B2B SaaS-платформе — исключение риска компрометации и смешивания архитектурных данных клиентов при высокой скорости выполнения запросов от MCP-сервера и веб-портала.

В исходной постановке задачи были сформулированы три гипотезы:
- **Вариант A (Graph per Tenant):** отдельный граф на каждого тенанта через `create_graph('tenant_<id>')`.
- **Вариант B (Shared Graph with tenant_id):** единый общий граф, где в свойствах вершин и ребер указывается `{tenant_id: '...'}`.
- **Вариант C (Schema per Tenant):** выделенная схема PostgreSQL на каждого клиента, внутри которой функционирует граф.

## 2. Оговорка: тождественность Вариантов A и C

В ходе анализа исходного кода и архитектуры Apache AGE установлено: **Вариант A и Вариант C технически тождественны.**

### Механика Apache AGE под капотом
1. В Apache AGE концепция графа физически реализована через схемы PostgreSQL (`pg_namespace`).
2. Команда `SELECT create_graph('tenant_x');`:
   - Создает запись в системном каталоге `ag_catalog.ag_graph` с уникальным идентификатором `graphid`.
   - Создает отдельную схему `CREATE SCHEMA tenant_x;`.
   - Создает в этой схеме базовые таблицы `_ag_label_vertex` и `_ag_label_edge`.
3. При создании новых типов вершин и ребер (например, `:Service`, `:DEPENDS_ON`) AGE автоматически создает в схеме `tenant_x` таблицы меток, которые наследуют базовые (`INHERITS (tenant_x._ag_label_vertex)`).
4. Запрос `SELECT * FROM cypher('tenant_x', $$ ... $$);` обращается напрямую к таблицам схемы `tenant_x`.

**Вывод:** В Apache AGE невозможно создать граф без создания схемы, как и невозможно создать независимый граф внутри произвольной пользовательской схемы иначе, чем сделав эту схему графом. Разделение на Вариант A и Вариант C является мнимым.

Реальное архитектурное сравнение происходит между:
1. **Изолированные графы (A, Graph/Schema per Tenant)**.
2. **Единый общий граф с дискриминатором (B, Shared Graph with tenant_id)**.

## 3. Результаты стресс-тестирования 50 графов

Для подтверждения жизнеспособности Варианта A был проведен стресс-тест в среде PostgreSQL 16 с Apache AGE 1.5.0 (Docker-контейнер `archon-age-benchmark`, скрипт [`tenant_isolation_research.sql`](tenant_isolation_research.sql)).

Тест воспроизводит полный жизненный цикл 50 тенантов:
1. **Инициализация (Provisioning):** последовательное создание 50 независимых графов.
2. **Наполнение данными и DDL меток:** вставка вершин (`:Service`, `:Database`) и ребер (`:DEPENDS_ON`) в каждый граф (создание 150 наследуемых таблиц меток).
3. **Чтение и обход графа (Traversal):** выполнение Cypher-запроса на сопоставление путей во всех 50 графах.
4. **Удаление тенантов (Deprovisioning / Cleanup):** каскадное удаление всех 50 графов через `drop_graph(..., true)`.

### Замеры времени выполнения

| Этап жизненного цикла | Операция | Суммарное время (50 графов) | Среднее время на 1 тенант |
| :--- | :--- | :--- | :--- |
| **1. Provisioning** | `create_graph('tenant_i')` | 1315.71 ms | ~26.3 ms |
| **2. Population + DDL** | `CREATE (s:Service)-[:DEPENDS_ON]->(d:Database)` | 988.15 ms | ~19.8 ms |
| **3. Read / Traversal** | `MATCH (s:Service)-[:DEPENDS_ON]->(d:Database)` | 39.34 ms | ~0.79 ms |
| **4. Offboarding / Drop** | `drop_graph('tenant_i', true)` | 379.98 ms | ~7.6 ms |

### Краткий анализ результатов теста
- Создание схемы и базовых таблиц графа занимает ~26 мс, что комфортно укладывается в требования к фоновому онбордингу клиентов.
- Создание меток сущностей на лету генерирует DDL таблиц схем без блокировки других тенантов.
- Обход путей выполняется со скоростью менее 1 мс на запрос благодаря компактности индексов схемы.
- Каскадное удаление через `drop_graph` мгновенно зачищает метаданные и таблицы, не порождая «мертвых» строк (dead tuples).

## 4. Сравнительный анализ подходов

| Критерий | Вариант A: Свой граф на клиента (Рекомендуемый) | Вариант B: Общий граф с `tenant_id` | Влияние на Archon |
| :--- | :--- | :--- | :--- |
| **Изоляция данных и безопасность** | **Физическая (Схемы СУБД).** Запросы выполняются строго в схеме тенанта `cypher('tenant_x', ...)`. Утечка невозможна без явной подмены имени графа в DAL. | **Логическая (Слой приложения).** Требует строгой дисциплины в коде: каждое условие `WHERE` и каждый шаг обхода должны содержать проверку `tenant_id`. | Из-за отсутствия поддержки нативного Row-Level Security внутри Cypher-функций AGE, Вариант A даёт критически важную для Enterprise страховку от ошибок разработчиков. |
| **OLTP-производительность (MCP и портал)** | **Высокая и предсказуемая.** Индексы компактны и изолированы. Граф клиента целиком помещается в память, нет эффекта «шумного соседа» по кэшу. | **Зависит от соседей.** Единый пул кэша и меньше дескрипторов файлов, но индексы составные и тяжёлые; активный клиент может вымывать кэш остальных. | Запросы от агентов в IDE (Cursor, Claude) требуют стабильного отклика < 1–5 мс без деградации из-за активности других организаций. |
| **Глобальная аналитика и ML (Admin views)** | **Сложно.** Для сбора общей статистики (например, «какая версия Java популярнее по всем клиентам?») нужен ресурсоёмкий опрос сотен схем. | **Идеально.** Вся статистика собирается одним простым агрегирующим запросом `GROUP BY` без фильтра по тенанту. | На этапе MVP оперативность контекста для агентов важнее глобальной аналитики. Для аналитики данные в будущем выгружаются в аналитическое DWH. |
| **Миграции и управление индексами** | **O(N) операций.** Добавление нового индекса или констрейнта требует цикла `FOR EACH tenant` по всем схемам клиентов. | **O(1) операция.** Индексы и правила создаются один раз на общих таблицах вершин и рёбер. | Инфраструктура Archon должна поддерживать циклическое применение миграций схемы тенанта при развёртывании релизов. |
| **Нагрузка на системный каталог (Postgres)** | **Высокая.** 1000 клиентов = тысячи таблиц. Это увеличивает размер `pg_class`, повышает расход памяти на соединение и усложняет `autovacuum`. | **Низкая.** Количество таблиц фиксировано. Postgres максимально эффективно использует кэш планов запросов (Plan Cache) и разделяемую память. | PostgreSQL стабильно держит до ~10–15 тыс. таблиц. Вариант A потребует шардирования по базам данных при превышении порога в 500–1000 клиентов. |
| **Удаление клиента (Offboarding / GDPR)** | **O(1) (Мгновенно).** Удаление схемы через `DROP CASCADE` высвобождает место на диске сразу, без деградации БД и фрагментации (bloat). | **O(N) (Интенсивно по I/O).** Множественные `DELETE` генерируют большой объём WAL и «мёртвые строки». Требуется тяжёлый `VACUUM` для возврата места. | Мгновенное удаление в Варианте A снимает риски нарушения SLA и требований GDPR при отключении корпоративных клиентов. |
| **Сложность DAL (Код приложения)** | **Простая логика запросов.** Графовые запросы пишутся чисто на предметную область в стандартном openCypher, без технических `tenant_id`. | **Сложная логика Cypher.** В AGE нет автоматической фильтрации путей. Приходится собирать запросы через конкатенацию или писать кастомный AST-парсер. | Для небольшой команды на старте чистый Cypher экономит недели разработки и упрощает потенциальную миграцию на Memgraph/Neo4j. |

### Пояснения и технические детали к таблице

1. **Почему в Варианте B не защищает Row-Level Security (RLS)?**  
   В обычных SQL-таблицах безопасность можно обеспечить механизмом RLS (автоматическая фильтрация строк по ID пользователя). Однако в Apache AGE запросы исполняются через графовый движок Cypher (`cypher('graph_name', ...)`). При поиске путей переменной длины (например, поиск цепочки вызовов `(a)-[:DEPENDS_ON*1..4]->(b)`) движок AGE обходит ребра через свои внутренние итераторы, где политики RLS не применяются. Если на каком-то звене пути не окажется явного условия `r.tenant_id = $id`, запрос уйдет в граф другого клиента.
2. **Почему удаление в Варианте B перегружает систему?**  
   Команда `drop_graph` в Варианте A просто удаляет схему с диска (аналогично удалению директории в файловой системе). В Варианте B вызов `DETACH DELETE` для тысяч сущностей клиента порождает миллионы записей в журнале транзакций (WAL), накладывает блокировки на общие таблицы ребер и оставляет в страницах памяти «мертвые строки» (dead tuples), требующие тяжелой процедуры очистки `VACUUM FULL`.
3. **Баланс безопасности и масштабируемости каталога:**  
   Для B2B SaaS, хранящего архитектуру и контракты сторонних корпораций, гарантия физической изоляции (Security) безусловно перевешивает накладные расходы на сопровождение системных таблиц `pg_class`. Потолок в 500–1000 тенантов на один инстанс полностью покрывает фазы MVP и масштабирования первого года, после чего архитектурно задействуется шардирование баз данных (Database Sharding).

## 5. Выявленные инженерные нюансы Варианта A

При реализации Варианта A команде платформы необходимо учесть три правила:

1. **Специфика автономного бэкапа схем через pg_dump:**  
   Поскольку связи графов и их внутренние `graphid` регистрируются в общем каталоге `ag_catalog.ag_graph`, стандартный вызов `pg_dump -n tenant_x` сохраняет таблицы схемы, но не содержит метаданных из `ag_catalog`. Для изолированного экспорта/импорта клиента в DAL модуля `model` должен быть предусмотрен логический экспорт в формате openCypher/JSON либо утилита синхронизации `ag_catalog` при восстановлении схемы.
2. **DDL-блокировки при онбординге:**  
   Вызовы `create_graph` берут кратковременные эксклюзивные блокировки на системные каталоги. Процесс онбординга нового клиента должен выполняться асинхронно в изолированной транзакции через воркер Temporal, не создавая конкуренции на быстрых запросах чтения.
3. **Шардирование при масштабировании:**  
   Слой доступа к данным (DAL) должен изначально уметь маршрутизировать запросы не только по имени графа, но и по пулу баз данных (Database Routing), чтобы плавно поддержать масштабирование после исчерпания лимита в 1000 клиентов.

## 6. Итоговая рекомендация (DoD 3)

**Однозначная рекомендация:** Принять **Вариант A (Graph per Tenant)** как стандарт архитектурной изоляции данных в Archon Managed SaaS и зафиксировать его в [ADR-0003](../../../docs/adr/0003-source-of-truth-and-tenant-isolation.md).

### Обоснование для включения в issue и ADR-0003:
1. **Zero Trust Isolation:** В архитектурном продукте enterprise-уровня риск смешивания данных топологии неприемлем. Вариант A дает 100% гарантию безопасности на уровне изоляции схем PostgreSQL.
2. **Чистый openCypher:** Запросы формируются без искусственных фильтров `{tenant_id: ...}`, что гарантирует переносимость DAL на специализированные графовые движки (Memgraph / Neo4j) без переписывания бизнес-логики.
3. **Мгновенный Offboarding:** Удаление графа клиента за миллисекунды гарантирует соблюдение требований GDPR / Enterprise Compliance без деградации базы данных.
4. **Достаточный запас масштабируемости для MVP:** Один инстанс PostgreSQL 16 комфортно обслуживает сотни изолированных клиентских графов. Горизонтальное масштабирование на этапе зрелости будет осуществляться шардированием баз тенантов (Database Sharding).
