# Технологический стек Archon

> Статус: Принят командой. Язык бэкенда — **Kotlin / JVM**.
> Формальная фиксация будет оформлена в виде ADR.

---

## 1. Главные принципы выбора технологий

1. **On-Premise First:** Система разворачивается в закрытых корпоративных контурах клиентов (K8s / Helm, air-gapped). Минимум сторонних внешних SaaS-зависимостей, простая и предсказуемая эксплуатация.
2. **Один язык на бэкенд — Kotlin / JVM:** Весь бэкенд пишем на Kotlin. Исключение — только LLM-модули на Python (см. п.3). Держать один основной стек критично при команде в 4 человека.
3. **Python только там, где есть LLM:** Python оставляем исключительно для модулей семантического анализа, эмбеддингов и RAG (`interpret`, `drift`), где экосистема нейросетей не имеет равных.
4. **Готовые enterprise-компоненты вместо велосипедов:** Для очередей, графов, авторизации и оркестрации берем зрелые проверенные Open-Source решения.
5. **Оптимизация потом:** GraalVM / native-image рассматриваем только после готовности основного функционала, как оптимизацию, а не как требование на старте.

## 2. Базовая инфраструктура и платформенные компоненты

Эти компоненты не зависят от языка бэкенда:

| Слой / Задача | Технология | Почему именно она |
| :--- | :--- | :--- |
| **Граф знаний + Реляционные данные** | **PostgreSQL 16+ с расширением Apache AGE** | Закрывает сразу две задачи: реляционные таблицы (пользователи, репозитории, настройки) и графовую модель (узлы архитектуры, связи, запросы openCypher) в единой СУБД. Без лицензионных рисков Neo4j в On-Premise. |
| **Векторная БД (RAG / Поиск)** | **Qdrant** | Быстрый векторный движок на Rust, легкий в деплое (один бинарник / контейнер), отличная поддержка фильтрации по метаданным. |
| **Шина событий и кэш** | **NATS JetStream + Redis** | NATS — сверхлегкий event bus для передачи задач между модулями. Redis — кэширование и временные состояния. |
| **Оркестрация пайплайнов** | **Temporal.io** | Управление сложными и долгими распределенными процессами (сканирование репозиториев, ретраи при падении LLM, шаги анализа). |
| **Политики архитектуры** | **Open Policy Agent (OPA / Rego)** | Индустриальный стандарт декларативных политик безопасности и архитектурных правил. |
| **Рендеринг C4-диаграмм** | **LikeC4 / React Flow** | LikeC4 — декларативное описание C4-архитектуры и рендеринг интерактивных схем. |
| **SSO / Аутентификация** | **Keycloak / OAuth2 Proxy** | Стандарт корпоративной авторизации (OIDC, SAML, LDAP/AD). |

## 3. Язык бэкенда: Kotlin / JVM (решение принято)

Развилку Go vs Kotlin закрываем в пользу **Kotlin / JVM** — это приоритет Паши и этого достаточно для всего ядра Archon.

### Почему Kotlin / JVM подходит

- Весь продукт общается через контракты (REST + события NATS + Temporal) — языку бэкенда всё равно, Spring это или что-то другое.
- **Temporal** имеет первоклассный Java/Kotlin SDK — для `runtime` это один из лучших вариантов.
- Keycloak, OPA, Qdrant, Apache AGE — работают поверх REST/SQL, от языка не зависят.

### Фреймворки — на выбор Паши

Приоритет Паши: **Spring Boot 3, Micronaut, на крайний случай Ktor**. Любой из них ок для Archon, архитектура не навязывает конкретный:

- **Micronaut + Kotlin** — быстрый старт, мало памяти, хорошо дружит с GraalVM native-image (удобно для пачки коротких job'ов на репо).
- **Spring Boot 3** — если Паша на нём быстрее всего — берём Spring. Экосистема и интеграция с Temporal того стоят. Цена — больше RAM и медленнее старт, для долгих Temporal-воркеров не критично.
- **Ktor** — лёгкий и функциональный, но DI/конфиг/метрики собираешь руками. Ок для API-слоя, больше ручной работы для остального.

Выбор конкретного фреймворка фиксируем отдельным решением Паши, стек это не ломает.

### GraalVM — после MVP

GraalVM / native-image пробуем **после готовности основного функционала**, как оптимизацию сервисов (быстрый старт, меньше памяти в K8s). На старте не блокируемся на нём.

### Про Go

Go из основного стека убираем. Допуск только как исключение: **1–2 отдельных сервиса на Go, если будет срочная необходимость** («горит — надо быстро выкатить»). Это не часть базового стека и не требует держать Go как второй язык для всего бэкенда.

## 4. Стек по 16 модулям системы

### Блок «Витрина» (Showcase)
* **`portal` (Веб-портал):**
  * **Стек:** TypeScript, React, Next.js / Vite, Tailwind CSS, shadcn/ui.
  * **Библиотеки:** `@likec4/core` / `@likec4/diagrams` (интерактивные графы C4), TanStack Query (кэш данных), TanStack Table.
* **`pr-bot` (Бот в Git/MR):**
  * **Стек:** Kotlin (Spring Boot 3 / Micronaut / Ktor).
  * **Библиотеки:** Kotlin Git-клиенты (GitHub/GitLab API), шаблонизатор Markdown-комментариев.
* **`chat-bot` (Бот в мессенджерах):**
  * **Стек:** Kotlin (или Python-микросервис рядом с LLM, если удобнее для RAG).
  * **Интеграции:** Slack Bolt SDK, Mattermost API, Telegram Bot API.
* **`export` (Экспорт отчетов):**
  * **Стек:** Kotlin / Node.js.
  * **Библиотеки:** Puppeteer / Playwright (генерация PDF из HTML/C4), генераторы Structurizr DSL / JSON.

### Блок «Решение» (Decision)
* **`assurance` (Жизненный цикл находок и рисков):**
  * **Стек:** Kotlin.
  * **Хранилище:** PostgreSQL (реляционная модель статусов, аудит-лог действий архитекторов, вердикты).

### Блок «Мозг» (Brain)
* **`model` (Хранилище графа знаний):**
  * **Стек:** Kotlin.
  * **Движок:** PostgreSQL + Apache AGE (доступ через SQL + openCypher), Apache Arrow/Memory для быстрой сборки графов.
* **`resolve` (Склейка сущностей между репо):**
  * **Стек:** Kotlin.
  * **Алгоритмы:** Графовые алгоритмы сопоставления контрактов, нечеткий поиск (`fuzzy matching`), нормализация эндпоинтов и топиков.
* **`policies` (Архитектурные политики):**
  * **Стек:** Kotlin + OPA.
  * **Библиотеки:** Open Policy Agent (in-process evaluation через OPA REST / sidecar).
* **`drift` (Детектор расхождений доков и кода):**
  * **Стек:** Python (FastAPI / Celery воркер).
  * **Библиотеки:** LlamaIndex / LangChain, sentence-transformers, интеграция с локальными LLM (vLLM / Ollama / OpenAI-compatible).

### Блок «Фабрика» (Factory)
* **`registry` (Реестр сервисов, словарь, конфигурация):**
  * **Стек:** Kotlin.
  * **Хранилище:** PostgreSQL + кэш в памяти.
* **`sources` (Коннекторы к источникам):**
  * **Стек:** Kotlin.
  * **Библиотеки:** JGit (Git), Confluence REST API client, Jira REST API client.
* **`extract` (Детерминированный парсер кода):**
  * **Стек:** Kotlin. Для мультиязычного парсинга (Tree-sitter) — при необходимости выносим Tree-sitter в маленький sidecar (Rust/Python) за gRPC/HTTP, ядро остаётся на Kotlin.
  * **Библиотеки:** JavaParser / Kotlin PSI / ANTLR для JVM-языков; OpenAPI parser, YAML/JSON Schema validators.
* **`interpret` (Семантический анализатор документации):**
  * **Стек:** Python.
  * **Библиотеки:** Unstructured.io (парсинг markdown/docx/pdf), LlamaIndex (RAG), Pydantic (валидация JSON-схем ответов LLM).
* **`reconcile` (Разрешение конфликтов фактов):**
  * **Стек:** Kotlin.
  * **Логика:** Матрица доверия источникам (AST факт > LLM предположение), слияние свойств в канонический Extraction Contract.

### Блок «Фундамент» (Foundation)
* **`runtime` (Оркестрация и бюджеты):**
  * **Стек:** Temporal.io Server + Kotlin SDK для воркеров, Prometheus/OpenTelemetry для сбора метрик затрат токенов.
* **`platform` (Аудит, права, безопасность):**
  * **Стек:** Kotlin + Keycloak (OIDC/SAML), Casbin (RBAC/ABAC), HashiCorp Vault (хранение токенов Git/Jira).
