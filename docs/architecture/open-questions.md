## 2. Актуальные открытые вопросы

### OQ-4. Разрешение противоречий источников

**Модуль:** `reconcile`  
**Приоритет:** High

Что делать, если детерминированный синтаксический контур (`extract`) извлек один факт, а семантический LLM-контур (`interpret`) выдвинул противоречащую гипотезу?

*Пример:* `extract` по сигнатурам кода определяет использование HTTP REST-клиента, а `interpret` на основе анализа текста README или комментариев утверждает, что сервис напрямую обращается к чужой БД.

**Что необходимо решить:**
1. **Правило приоритета:** зафиксировать жесткий приоритет детерминированных фактов над выводами модели (синтаксис и AST побеждают гипотезы).
2. **Модель противоречий:** как фиксировать конфликт источников в графе (`Finding` категории `reconciliation_conflict` со ссылками на доказательства обеих сторон).
3. **Очередь верификации:** автоматическая эскалация неразрешимых конфликтов в инбокс модуля `assurance` для подтверждения архитектором или тимлидом.

### OQ-6. Событийная модель

**Модули:** `sources`, `extract`, `pr-bot`  
**Приоритет:** Medium

Как устроен сквозной конвейер событий: `Git Push / Webhook -> очередь задач -> инкрементальный анализ -> уведомления / checks`.

**Что необходимо решить:**
1. **Инкрементальный анализ (Diff vs Full Scan):**
   - Для PR-бота (`pr-bot`) критично анализировать только дифф измененных файлов запроса на слияние (< 10 секунд).
   - Для фонового аудита ветки по умолчанию выполняется полный периодический прогон.
2. **Транспорт событий:** формат вебхук-событий через Ingress шлюза `platform` (`/api/v1/webhooks/*`) и постановка в очередь задач Redis/BullMQ.
3. **Обратная связь:** интеграция статусов проверок (GitHub Checks API / GitLab Commit Statuses) при обнаружении дрейфа.

### OQ-7. Склейка сущностей между репозиториями

**Модуль:** `resolve`  
**Приоритет:** High

Как автоматически понять, что топик Kafka, таблица базы данных или внешний сервис, упоминаемые в 10 разных репозиториях под слегка различающимися именами, — это один и тот же физический объект, а не 10 изолированных узлов?

**Контекст:**
- В раннем прототипе `archmap` велся ручной справочник `shared/externals.c4`, который требовал постоянного ручного обновления и приводил к рассинхрону.
- `resolve` — самый сложный алгоритмический модуль продукта, строящий агрегированный C0-ландшафт всей организации.

**Варианты решения:**
1. Эвристики сопоставления URL/DSN подключений из файлов конфигураций (`application.yml`, `docker-compose.yml`, K8s ConfigMap).
2. Сопоставление клиентских библиотек и OpenAPI-спецификаций провайдера.
3. Склейка по идентификаторам развертывания (K8s Service / Namespace identity).
4. Нормализация через канонический словарь корпуса ([OQ-9](#oq-9-канонический-словарь)).

### OQ-9. Канонический словарь

**Модуль:** `registry`  
**Приоритет:** High

Кто и как формирует и поддерживает `vocabulary.json` — канонический словарь доменных терминов, продуктов, команд и сервисов.

**Что необходимо решить:**
1. **Источник словаря:** это статический конфиг клиента, настраиваемый администратором через веб-портал `portal`, или обучаемая модель синонимов?
2. **Область применения:** используется модулями `sources`, `resolve` (для дедупликации сущностей) и `policies` (для проверки правил принадлежности к доменам).
3. **Версионирование словаря:** изменение словаря терминов и тегов влияет на результаты межрепозиторного анализа и требует пересчета связей.

### OQ-15. Рантайм и стоимость

**Модуль:** `runtime`  
**Приоритет:** Medium

Как построить управление очередями задач, лимитами затрат на языковые модели и поведением системы при исчерпании квот.

**Что необходимо решить:**
1. **Бюджетные потолки (Cost Caps):**
   - Максимальный лимит токенов/стоимости на один анализ репозитория.
   - Месячный бюджет арендатора (tenant quota) в рамках тарифа Managed SaaS.
2. **Graceful Degradation:** поведение пайплайна при исчерпании LLM-квоты — автоматическое переключение на чистый детерминированный разбор (`extract`), сохраняющий базовую топологию и предупреждающий пользователя об отключении семантического анализа.
3. **Устойчивость к частичным сбоям:** ошибка анализа одного нестандартного репозитория в организации не должна прерывать прогон по остальным сервисам корпуса.

### OQ-17. Каталог: секция портала или публичный API

**Модуль:** `portal`  
**Приоритет:** Low

Форма поставки каталога сервисов (Service Catalog & Service Passport).

**Текущий статус:**
- **Принят дефолт ([ADR-0004](../adr/0004-module-decomposition-revision-1.md)):** каталог сервисов реализуется как ключевая визуальная секция веб-портала `portal`.
- Вопрос остается открытым на будущее: если появится спрос на использование каталога Archon как внешнего service registry для сторонних систем (интеграция по типу Backstage Software Catalog), модуль `catalog` может выделиться в самостоятельный сервис Public API.

### OQ-22. Формат и скоуп публичного API

<a id="oq-22-формат-и-скоуп-публичного-api"></a>
**Модули:** `platform`, `portal`, `pr-bot`  
**Приоритет:** Medium (Фаза 1)  
**Контекст:** Открыт из [ADR-0006](../adr/0006-saas-delivery-model-and-ai-native-source-of-truth.md) и [`iaas-to-saas-migration.md`](../research/iaas-to-saas-migration.md).

Пользователям, внешним скриптам и CI/CD пайплайнам требуется программный доступ к возможностям Archon.

**Что необходимо решить:**
1. **Протокол:** REST (OpenAPI 3.1) для типовых операций и CI-гейтов (`POST /v1/checks/pr`, `/api/v1/webhooks/*`) против GraphQL для гибких выборок графа связей. Базовый консенсус — REST API на этапе MVP.
2. **Скоуп MVP:**
   - Ingestion API: прием вебхуков от Git-провайдеров.
   - Query API: запросы узлов графа, зависимостей и паспорта сервиса.
   - Quality Gate API: проверка блокировки коммитов при наличии критического архитектурного дрейфа.
3. **Аутентификация и rate-limiting:** сервисные API-ключи арендатора через платформенный шлюз `platform`.

### OQ-23. Поддержка закрытых контуров: анализ вариантов (Air-Gapped / Strict On-Premise)

<a id="oq-23-поддержка-закрытых-контуров-анализ-вариантов-air-gapped-strict-on-premise"></a>
<a id="oq-23-поддержка-закрытых-контуров-hybrid--local-agent"></a>
**Модули:** `sources`, `platform`, `extract`  
**Приоритет:** High  
**Контекст:** Открыт из [ADR-0006](../adr/0006-saas-delivery-model-and-ai-native-source-of-truth.md). В enterprise-сегменте (банки, телеком, госструктуры) требования безопасности часто запрещают передачу исходного кода во внешнее облако или предоставление облачному SaaS прямого доступа во внутреннюю сеть с корпоративным GitLab.

**Сравнительный анализ вариантов:**

#### Вариант 1. Архитектура «Local Scanner / Hybrid Agent» (Рекомендуемый для Фазы 2)
- **Принцип работы:** в закрытом контуре клиента (в CI runner или K8s) запускается легкий CLI/контейнер `archon-scanner` на базе `extract`. Он парсит AST и манифесты локально, формируя анонимизированный граф по схеме Extraction Contract v1.0.
- **Безопасность:** исходный код никогда не покидает периметр заказчика; в облачный SaaS по защищенному каналу (mTLS / HTTPS) передаются исключительно структурные метаданные (типы, эндпоинты, связи).
- **Плюсы:** нулевой риск утечки кода, нет необходимости разворачивать и сопровождать тяжелые базы данных и оркестратор на стороне клиента.
- **Ограничения:** для семантического анализа (`interpret`) требуется либо локальная LLM в сети заказчика, либо отправка обезличенных цитат.

#### Вариант 2. Dedicated Cloud / Single-Tenant VPC
- Под enterprise-клиента разворачивается выделенный изолированный экземпляр Archon в отдельном облачном VPC (AWS, GCP, Yandex Cloud) с подключением к корпоративной сети через IPSec VPN или Direct Connect.
- Полная изоляция инфраструктуры, но требует индивидуального сопровождения.

#### Вариант 3. Full On-Premises / Air-Gapped Appliance
- Полная автономная поставка через Helm-чарт со всеми сервисами, базами данных и локальными LLM (vLLM / Ollama).
- Максимальная изоляция, но высокий Time-to-Value и повышенные требования к инфраструктуре клиента (наличие GPU-узлов).

**Вывод по OQ-23:**
1. Для MVP реализуется чистый Managed SaaS с архитектурой Privacy-by-default (клонирование в эфемерную память и немедленное удаление).
2. Для первых закрытых enterprise-клиентов прорабатывается **Вариант 1 (Hybrid Local Scanner)**.

### OQ-24. Модель авторизации, прав и аудита запросов к MCP Server

<a id="oq-24-модель-авторизации-прав-и-аудита-запросов-к-mcp-server"></a>
<a id="oq-24-авторизация-роли-и-аудит-запросов-к-mcp-server"></a>
**Модули:** `platform`, `mcp`  
**Приоритет:** High  
**Контекст:** Открыт из [ADR-0006](../adr/0006-saas-delivery-model-and-ai-native-source-of-truth.md). MCP-сервер становится ключевой точкой интеграции с AI-агентами разработчиков в IDE (Cursor, Windsurf, Copilot, Claude Code).

**Что необходимо решить:**
1. **Аутентификация агентов:** персональные scoped API-токены разработчиков и организационные сервисные токены для CI-ботов.
2. **Гранулярность доступа:**
   - Ограничение видимости узлов графа: AI-агент имеет доступ только к архитектурным контрактам тех репозиториев, на которые у разработчика есть права в Git.
   - Скрытие чувствительных контрактов (платежные шлюзы, криптографические сервисы).
3. **Аудит и безопасность:**
   - Логирование вызовов инструментов MCP: какие узлы графа и правила запрашивались перед кодогенерацией.
   - Защита от prompt injection через отдачу проверенного контекста (`evidence_files`).

#### OQ-2. Где хранить модель данных
<a id="oq-2-source-of-truth-модели-данных"></a>
<a id="oq-2-где-хранить-модель-данных"></a>
**Закрыт [ADR-0003](../adr/0003-source-of-truth-and-tenant-isolation.md) (2026-09-05).**  
Единый агрегированный Source of Truth архитектуры хранится в графовой базе данных. Git выступает источником сырого кода (Source of Code). Факты из коммитов проходят верификацию и вливаются в граф. Запросы MCP, портала и PR-бота обслуживаются базой в реальном времени.

#### OQ-3. Контракт извлечения
<a id="oq-3-контракт-извлечения"></a>
<a id="oq-3-границы-и-версионирование-extraction-contract"></a>

#### OQ-5. Хранилище графа и запросы

<a id="oq-8-физическая-топология"></a>
<a id="oq-8-физическая-топология-упаковка-модулей-и-оркестрация-saas"></a>
**Закрыт [ADR-0007](../adr/0007-saas-process-topology-and-packaging.md) (2026-09-07), спецификация — [deployment.md](deployment.md).**  
Все 17 логических модулей фабрики собираются в 3 сборочные единицы:
1. `archon-core-service` (Kotlin / JVM) — ядро, REST API, вебхуки, детерминированный разбор, reconcile, DAL к AGE.
2. `archon-ai-service` (Python) — LLM-семантика (`interpret`), векторный поиск, FastMCP сервер.
3. `archon-portal` (TypeScript / React) — веб-витрина с LikeC4 viewer.  
Код клиентов клонируется исключительно во временный RAM-диск (`/dev/shm`) и удаляется после извлечения (Privacy-by-default).

#### OQ-10. Граница скоупа продукта
<a id="oq-10-граница-скоупа-архон-как-слой-знаний-vs-полная-docs-as-code-платформа"></a>
**Закрыт в [ADR-0005](../adr/0005-product-scope-and-delivery-model.md) (2026-09-02).**  
Archon позиционируется как слой знаний (Source of Truth) поверх существующей экосистемы клиента, а не как замена инструментам Git, CI/CD или таск-трекерам.

#### OQ-11. Разделение контура извлечения
<a id="oq-11-разделение-экстрактора-детерминированный--интерпретатор--примирение"></a>
**Закрыт в [ADR-0004](../adr/0004-module-decomposition-revision-1.md).**  
Монолитный контур разбора разделен на три независимых модуля: `extract` (синтаксический разбор), `interpret` (LLM-семантика) и `reconcile` (примирение фактов и происхождение).

#### OQ-12. Где живёт finding и его lifecycle
<a id="oq-12-где-живёт-находка-finding-и-её-lifecycle"></a>
**Закрыт в [ADR-0004](../adr/0004-module-decomposition-revision-1.md).**  
Управление находками архитектурных правил (`policies`) и документационного дрейфа (`drift`) объединено в модуле `assurance`.

#### OQ-13. Слой глобальной склейки сущностей
<a id="oq-13-слой-глобальной-склейки-сущностей-по-корпусу"></a>
**Закрыт в [ADR-0004](../adr/0004-module-decomposition-revision-1.md).**  
Выделен отдельный логический модуль `resolve` для построения целостного ландшафта поверх графа всех репозиториев организации.

#### OQ-14. Модуль человеческого контура
<a id="oq-14-модуль-человеческого-контура-ревью-доверие-принятие-риска"></a>
**Закрыт в [ADR-0004](../adr/0004-module-decomposition-revision-1.md).**  
Создан модуль `assurance`, реализующий жизненный цикл верификации человеком: принятие рисков, подтверждение гипотез, подавление ложных срабатываний.

#### OQ-16. Реестр корпуса и конфигурация клиента

#### OQ-18. Модель поставки: переход к Managed SaaS
<a id="oq-18-модель-поставки-переход-от-cliself-hosted-к-managed-saas"></a>

#### OQ-19. Генерация docs-as-code артефактов
<a id="oq-19-генерация-docs-as-code-артефактов-agentsmd-c4"></a>
<a id="oq-19-генерация-docs-as-code-артефактов"></a>
