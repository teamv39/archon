## OQ-1. Судьба прототипа archmap

**Статус:** закрыт [ADR-0002](../adr/0002-archmap-fate.md) (2026-09-04).

Решение:
1. Рантайм и инфраструктуру прототипа (n8n, TiMe-бот, GitLab Pages loop, хранение PAT в n8n Data Table) списать и архивировать.
2. JSON-контракт извлечения (Extraction Contract v1.0) принять как основу OQ-3 с обязательным сохранением `evidence_files` (защита от галлюцинаций), `confidence`, `uncertainties`, `k8s_hints` и `flows`.
3. Двухфазный контур отбора (File Selector Agent с правилом представительства + Architecture Extractor Agent) интегрировать в модуль `interpret`, дополнив детерминированным анализом фактов в `extract`.
4. Алгоритмическое ядро `json_to_likec4.py` (транслятор в DSL LikeC4, генерация C1–C3 и dynamic flows, подъем связей, детекция висячих элементов и `#manual_check`) портировать в модули `portal` и `export`.
5. Ручной файл `shared/externals.c4` списать; глобальную склейку сущностей передать модулям `resolve` (OQ-7) и `registry` (OQ-9).

## OQ-2. Где хранить модель данных

**Блокирует код.** Определяет весь модуль `model` и половину контура извлечения.

Граф связей между сервисами — это центр всей системы. Где его хранить?

Варианты:
- (a) **В Git-файлах** — документация как код, история из коробки. Минус: сложно делать запросы к графу.
- (b) **В графовой БД** — удобно делать запросы. Минус: "документация" становится базой данных, её нельзя ревьюить как обычный код.
- (c) **Гибрид** — Git как источник правды (`.c4`-файлы), БД как индекс для запросов. Индекс можно пересобрать из Git в любой момент.

Гибрид выглядит естественным продолжением того, что уже сделано в прототипе, но нужно решить, что победит при расхождении.

## OQ-4. Разрешение противоречий

Что делать, если детерминированный контур (`extract`) сказал одно, а LLM-контур (`interpret`) сказал другое?

Например, `extract` считает, что сервис использует HTTP-клиент, а `interpret` думает, что это прямое подключение к БД.

Открытое: приоритет источников, модель конфликтов, как это видно пользователю. Владелец — модуль `reconcile`.

## OQ-7. Склейка сущностей между репозиториями

Как понять, что одна и та же Kafka-топик или база данных, встречающиеся в двух разных репозиториях, — это один объект, а не два?

## OQ-8. Физическая топология

**Блокирует код.** Отвечает на вопрос "как модули разворачиваются и взаимодействуют физически в SaaS-модели".

В связи с переходом на Managed SaaS (ADR-0006) локальный all-in-one бинарник перестает быть целевой топологией MVP. Топология разделяется на сервисные контуры в нашей облачной инфраструктуре:

1. **Client / Gateway Layer:**
   - Web SPA (React/LikeC4 Portal)
   - API & MCP Gateway (маршрутизация, JWT/API-key авторизация, троттлинг, SSE/JSON-RPC)
2. **Worker / Orchestration Layer:**
   - Temporal Cluster (оркестрация многошаговых пайплайнов анализа, ретраи)
   - Stateless Extract & Interpret Workers (выкачивание AST, вызовы LLM, reconcile)
3. **Storage Layer:**
   - PostgreSQL 16 + Apache AGE (мультитенантный граф знаний и реляционные данные)
   - Qdrant (векторный поиск по чанкам кода и архитектурным докам)
   - Redis / NATS (кэширование, шина событий, pub/sub для обновлений портала)

Открытые вопросы топологии:
- Конфигурация multi-tenancy в PostgreSQL + AGE (схемы per-tenant vs общие таблицы с tenant_id).
- Изоляция воркеров при парсинге репозиториев (gVisor/Firecracker microVM vs эфемерные K8s pods).

## OQ-23. Поддержка закрытых контуров: архитектурный анализ вариантов (Air-Gapped / Strict On-Premise)

**Контекст:**
Переход к Managed SaaS (ADR-0006) решает проблему Time-to-Value для большинства клиентов. Однако в enterprise-сегменте (финтех, банки, телеком, критическая инфраструктура) требования безопасности часто запрещают передачу исходного кода во внешнее облако или предоставление облачному сервису доступа к закрытым корпоративным Git-репозиториям (GitLab on-premise, Bitbucket Server).

Ниже приведен предварительный сравнительный анализ вариантов реализации Archon для закрытых периметров:

### Вариант 1. Архитектура «Local Scanner / Hybrid Agent» (Рекомендуемый для детальной проработки)
* **Как работает:**
  1. В закрытом контуре заказчика (в runner CI/CD, на машине разработчика или как сервис в K8s) разворачивается легковесный бинарник — `archon-scanner` (на базе модулей `extract` и Tree-sitter).
  2. Сканер локально парсит репозиторий, извлекает AST, схемы и контракты, формируя анонимизированный граф фактов по строгой схеме Extraction Contract (OQ-3).
  3. **Исходный код никогда не покидает локальную сеть заказчика.** В облачный Archon SaaS по защищенному каналу (mTLS / HTTPS) передаются исключительно метаданные (имена типов, границы модулей, сигнатуры API, ребра графа).
  4. Облачный Archon агрегирует метаданные, строит межрепозиторный граф (`resolve`), выявляет drift и отдает контекст через Web-портал и MCP.
* **Плюсы:**
  - Нулевой риск утечки исходного кода: передаются только метаданные и сигнатуры интерфейсов.
  - Клиенту не нужно администрировать сложные распределенные хранилища (AGE, Qdrant) и оркестратор (Temporal).
  - Минимальные накладные расходы на эксплуатацию.
* **Сложности / Риски:**
  - Модуль `interpret` (семантический разбор неструктурированных доков): требует либо использования локальной LLM в контуре клиента, либо псевдонимизации и отправки текстовых фрагментов в облачную LLM.
  - Требует исходящего HTTPS-доступа из корпоративной сети к SaaS API Archon (через corporate proxy). Не подходит для абсолютно изолированных air-gapped контуров без внешней сети.

### Вариант 2. Dedicated Cloud / Single-Tenant VPC
* **Как работает:**
  Под enterprise-клиента разворачивается выделенный изолированный экземпляр Archon в отдельном облачном VPC (AWS, GCP, Yandex Cloud) с подключением к корпоративной сети через IPSec VPN или Direct Connect.
* **Плюсы:**
  - Полная изоляция данных на уровне инфраструктуры.
  - Все возможности SaaS (`interpret`, полный пайплайн) без ограничений.
  - Эксплуатацию ведет команда Archon.
* **Сложности / Риски:**
  - Высокая себестоимость поддержки (требуется отдельное сопровождение каждого инстанса).
  - Долгий цикл продажи и настройки сетевого периметра.

### Вариант 3. Full On-Premises / Air-Gapped Appliance
* **Как работает:**
  Archon поставляется как автономный Helm-чарт со всеми сервисами внутри: базы данных, оркестратор, локальный инференс LLM (vLLM / Ollama с открытыми моделями).
* **Плюсы:**
  - Работает в 100% изолированных сетях без какого-либо выхода в интернет.
* **Сложности / Риски:**
  - Возврат к проблемам высокого Time-to-Value и сложного саппорта.
  - Требует наличия мощных GPU у заказчика для качественной работы локальных LLM.

### Вывод по OQ-23:
1. Для MVP реализуется чистый Managed SaaS с политикой Privacy-by-default.
2. Для первых enterprise-клиентов с ограничениями безопасности проектируется **Вариант 1 (Hybrid Local Scanner)** как наиболее технологичный и экономически оправданный.
3. Варианты 2 и 3 откладываются до появления стратегических контрактов с соответствующим бюджетом.

## OQ-24. Модель авторизации, прав и аудита запросов к MCP Server

**Открыт из ADR-0006.**
MCP-сервер становится ключевой точкой интеграции с AI-агентами (Cursor, Copilot, Claude Code).

Нужно определить:
1. **Аутентификация агентов:**
   - Персональные scoped API-токены разработчиков.
   - Организационные сервисные токены для CI/CD-агентов.
2. **Гранулярность доступа:**
   - Доступ только к графу репозиториев, на которые у разработчика есть права в Git-хостинге (sync прав через OAuth).
   - Ограничение видимости чувствительных архитектурных контрактов (например, платежные или криптографические сервисы).
3. **Аудит и безопасность (Compliance):**
   - Логирование запросов агента: какие узлы графа и правила запрашивались перед генерацией кода.
   - Защита от prompt injection через отдаваемый контекст.
