# User Journeys: сквозные сценарии

Назначение документа: проверить декомпозицию на модули. Это не требования к UI и
не маркетинговые сценарии — это тесты архитектуры. Каждый сценарий проводится
сквозь модули (`modules/README.md`), и всё, где сценарий не проходит чисто,
есть дефект декомпозиции или отсутствующий модуль.

**Статус: гипотезы.** Ни один сценарий пока не подтверждён интервью. Формат
расчёта: после 5-7 интервью (research/README.md) сценарии получают пометку
`confirmed` / `adjusted` / `dropped` — но уже сейчас они годятся как инструмент
проверки границ, потому что взяты из болей, зафиксированных в пре-ресерче.

## Роли

| Роль | Кто | Главный вопрос, на который отвечает Архон |
| :--- | :--- | :--- |
| Архитектор направления | владеет картой C0-C1, отвечает за связность | "что реально происходит в моих продуктах и где нарушают правила" |
| Tech Lead сервиса | владеет 1-3 сервисами | "что я сломаю этим релизом и что обо мне спросят новые люди" |
| Инженер-новичок | входит в незнакомый сервис | "как это устроено и к кому бежать" |
| Дежурный / SRE | тушит инцидент | "что упадёт следом и кто владелец" |
| Security / CISO | проводит аудит | "какие потоки данных никто не декларировал" |
| Владелец документации (PM/аналитик) | отвечает за Confluence | "какие мои страницы уже врут" |

## J1. Онбординг новичка

**Триггер:** новый инженер получил доступ к репозиторию, спрашивает "где читать".
**Успех:** через час может назвать 5 зависимостей своего сервиса и не отвлекает сеньора.

| Шаг | Что происходит | Модули |
| :--- | :--- | :--- |
| 1 | Новичок открывает карточку своего сервиса | d2 (витрина), m2 (данные карточки) |
| 2 | Видит C1/C2 диаграмму, контракты, владельцев из Jira, ссылки на живые доки | d1, m2, e2(Jira) |
| 3 | Кликает по "эта страница может устареть" | m4 |
| 4 | Хочет провалиться глубже в компонент | d1 (C3), m1 (LLM-слой) |

**Что этот сценарий требует от системы:**
- Карточка сервиса собирается из разных модулей без дублирования truth (иначе
  Passport станет второй ложью) — это проверяет границу `d2`/`m2`.
- Нужна стабильная ссылка на элемент графа (deep link), иначе новичок не
  "провалится" из ответа бота или из карточки.
- **Проверка:** кто такие `d2 catalog` и `d1 portal`? Они оба про "смотреть
  карточку сервиса". Граница не определена.

## J2. Оценка перед изменением (impact analysis)

**Триггер:** техлид собирается менять контракт/схему БД/топик.
**Успех:** до кода знает, кто сломается, и предупреждает владельцев.

| Шаг | Что происходит | Модули |
| :--- | :--- | :--- |
| 1 | Запрос "кто потребляет этот контракт" | m2 query API |
| 2 | Ответ: список сервисов + команды (через Jira) | m2, e2 |
| 3 | Изменение уходит в PR, бот подсвечивает последствий | d3, m1(инкрементальный) |
| 4 | Нарушение правила попадает в дашборд | m3, d1 |

**Что требует:**
- Запрос по графу с задержкой, годной для интерактива (OQ-5 это определяет).
- Инкрементальный `m1` на diff, не полный прогон.
- **Проверка:** `d3` описан как "комментатор", но по факту он consumer m2 и m3
  одновременно. Тест: если убрать `d3`, `d1` должен уметь показать то же самое.
  Да — значит `d3` это канал, а не модуль-источник. Совпадает с категорией
  delivery. Чисто.

## J3. Инцидент: что упадёт следом

**Триггер:** упал сервис X, дежурный в чуме, MTTR идёт.
**Успех:** за минуту понятно, какие downstream-сервисы задеты и кому писать.

| Шаг | Что происходит | Модули |
| :--- | :--- | :--- |
| 1 | Запрос из мессенджера "что зависит от X" | d4, m2 |
| 2 | Ответ с владельцами и контактами | m2, e2(Jira) |
| 3 | В карточке X видно, что зависимость Y была принята как риск | m3 |

**Что требует:**
- Ответ без входа в портал, прямо в чате: то есть `d4` должен иметь
  read-only доступ к m2 по API — ещё одна проверка "доставка читает, не хранит".
- Сценарий отказоустойчивости: во время инцидента Архон должен не пасть вместе с
  тем, что падает. Это NFR-запрос, которого сейчас в `nfr/` нет.
- **Проверка:** нужна ли актуальность графа в реальном времени? Если граф
  обновляется раз в сутки, дежурный получит врет. Отсюда — требование на
  `OQ-6` (event model) и, возможно, отдельный SLO freshness в NFR.

## J4. Релизный гейт: архитектурный CI

**Триггер:** PR пытается смержиться в master.
**Успех:** merge заблокирован или разрешён по правилам команды, без участия
архитектора руками.

| Шаг | Что происходит | Модули |
| :--- | :--- | :--- |
| 1 | Webhook о PR | e2 |
| 2 | Инкрементальный анализ diff | m1 |
| 3 | Сличение с правилами, расчёт нарушений | m2, m3 |
| 4 | Статус-чек + комментарий | d3 |
| 5 | Команда принимает риск (с обоснованием) | m3, d1, e1(audit) |

**Что требует:**
- Задержка цикла < комфортной для разработчика (NFR-число, пока ненаучное).
- Язык правил, который команда может написать сама, без релиза (`m3` как
  rules-as-code).
- **Проверка:** шаг 5 — workflow принятия риска — это UI (`d1`), данные (`m2`)
  и правила (`m3`) одновременно. Где лежит accepted risk? Если в `m3` — то
  почему он влияет на граф? Если в `m2` — то `m3` stateless? Граница не
  определена, требует ADR.

## J5. Протухание Confluence (миссия Zero Drift)

**Триггер:** код уехал, страница в Confluence осталась полугодовой давности.
**Успех:** владелец документа получает конкретный алерт: "вот утверждение, вот
факт из кода, вот дата расхождения".

| Шаг | Что происходит | Модули |
| :--- | :--- | :--- |
| 1 | Индексация Confluence, вычленение claims | m4, e2 |
| 2 | Сличение claims с фактами | m4, m2 |
| 3 | Алерт владельцу + ссылка на доказательство | m4, e2(Jira), d1 |
| 4 | Хозяин документа правит страницу, алерт закрывается | m4 (повторная индексация) |

**Что требует:**
- Утверждение в документе обязано быть привязано к узлу графа. Это самая
  слабая часть модели: привязка "текст -> узел" не определена (OQ-3, OQ-9).
- **Проверка:** кто источник правды про документ — реестр документов в `m4` или
  узлы `DOCUMENTED_BY` в графе (`data-model.md`)? Сейчас и то и другое.
  Дублирование — кандидат на дефект.

## J6. Аудит теневых интеграций (CISO)

**Триггер:** регуляторный аудит, вопрос "покажите все потоки ПДн между системами".
**Успех:** выгрузка фактических потоков + перечень мест, где данные идут мимо
декларированных границ.

| Шаг | Что происходит | Модули |
| :--- | :--- | :--- |
| 1 | Запрос "все потоки данных сервиса X" | m2 |
| 2 | Правила ищут обход gateway / недекларированный канал | m3 |
| 3 | Экспорт отчета | d1 (или отдельный export-канал?) |
| 4 | Права: у аудитора доступ только к нужной области | e1 |

**Что требует:**
- Типизация рёбер графа по данным (какой поток содержит ПДн) — в текущей
  модели данных этого атрибута нет вообще.
- **Проверка:** экспорт отчёта — это `d1`? Или отдельный канал `d5 report`?
  Регулярная выгрузка для регулятора не похожа на просмотр в браузере. Возможно
  недостающий модуль.
- **Проверка e1:** multi-tenancy здесь обязателен, но в NFR он заявлен без
  сценария. Сценарий закрыл требование.

## Что показали сценарии (сводка дефектов)

| # | Находка | Куда |
| :--- | :--- | :--- |
| F1 | Граница `d1 portal` / `d2 catalog` не определена: оба про просмотр карточки | нужно уточнить или слить |
| F2 | Нет stable deep link на элемент графа — ломает J1, J3, J4 | требование к `m2`, кандидат в ADR |
| F3 | Freshness графа как SLA не определена — J3 даёт врет при устаревшем графе | NFR + OQ-6 |
| F4 | Неясно, где физически живут `accepted risk` | граница `m3`/`m2`, кандидат в ADR |
| F5 | Дублирование реестра документов (`m4` vs `DOCUMENTED_BY` в графе) | candidate дефект модели данных |
| F6 | Нет атрибутов данных на рёбрах (ПДн, чувствительность) — J6 не проходит | `data-model.md` неполон |
| F7 | Экспорт/отчётность регулятору не описана ни одним каналом | возможный `d5` или часть `d1` |
| F8 | `d3` прошёл проверку как чистый канал доставки (хорошая новость) | — |
| F9 | Ни один сценарий не использует `e2` как "источник владельцев" явно, но J1-J6 на нём висят: `e2` недооценён как модуль, возможно должен быть шире (org/ownership graph) | пересмотр `e2` |

F1-F7 — реальный выход этого документа. Это не требования к фичам, а прорехи в
нашей же декомпозиции, которые без сценариев всплыли бы в середине разработки.
