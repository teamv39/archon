Вопрос анализа: где Archon уникален, а где догоняет. Задача — не
перечислить фичи конкурентов, а понять, что они принципиально не
закрывают из Zero Drift.

## Профиль по продуктам

### Backstage (Spotify, CNCF)

Что это: OSS-платформа для сборки внутреннего портала. Ядро —
software catalog (Component, System, API, Resource) + TechDocs
(MkDocs за ширмой) + плагины. Всё остальное — экосистема.

Сильные стороны:
- Стандарт де-факто для каталога, огромный реестр плагинов.
- Self-host, зрелое комьюнити, CNCF.
- Гибкость: портал можно собрать под себя.

Ограничения для Archon-сценария:
- Не знает про drift. TechDocs рендерит то, что лежит в репо; что доки
  врут — не проверяет. Сверка с кодом — внешняя задача.
- C4 — сторонний плагин, не связан с кодом.
- Порог входа высокий: Backstage — фреймворк, а не готовый продукт;
  требует команды для поддержки самого Backstage.
- Policies — через TechInsights/Maturity плагины, но это линтеры
  каталога, не анализатор архитектуры.

Урок для Archon: `portal` Archon не должен повторять Backstage как
фреймворк. Наша ставка — не каталог ради каталога, а связка
`model → drift/policies → assurance → portal/pr-bot`. Если делаем
portal совместимым по API/catalog-info — получаем лёгкую миграцию
для тех, у кого Backstage уже есть.

### Port

Что это: SaaS IDP, no-code/low-code. Идея — Blueprint
(схема сущностей) + интеграции (Git, K8s, CI, облака, incident
tools) + self-service actions + scorecards.

Сильные стороны:
- Быстрый старт без разработки портала.
- Богатые интеграции, хороший UX для платформенных команд.
- Scorecards закрывают часть governance.

Ограничения:
- SaaS-only — конфликт с on-prem требованием ряда целевых клиентов
  Archon (NFR).
- Drift понимает как несоответствие scorecard'ам/интеграциям, но не
  как расхождение документ-код на уровне семантики.
- Семантика кода (что сервис *делает*) — вне модели; анализ
  архитектуры поверхностный.
- Ценообразование per-developer, быстро растёт — фактор для крупных
  инсталляций (проверить актуальный прайс).

Урок для Archon: Port — ориентир для UX `registry` (что анализировать)
и `portal` (scorecards → `assurance`). Но транспорт (`sources`) у
Archon обязан быть self-hosted и расширяемым без вендор-лока.

### OpsLevel

Что это: SaaS-портал, фокус — service catalog + maturity/checks +
campaigns (массовые инициативы по исправлению).

Сильные стороны:
- Лучшие в классе checks/campaigns — близко к идее `policies` +
  `assurance` у Archon.
- Хорошая отчётность для менеджмента (экспорт, зрелость).

Ограничения:
- Как и Port — SaaS, нет C4, нет семантического анализа кода.
- Drift — через проверки, а не через извлечение фактов из кода/доков
  и их сверку.
- Каталог-тюнинг, а не knowledge graph.

Урок для Archon: модель campaigns → прообраз `assurance` (жизненный
цикл находки) и `pr-bot`. У OpsLevel стоит подсмотреть метрики
зрелости и отчёты (`export`).

### Compass (Atlassian)

Что это: каталог компонентов Atlassian, нативно встроен в Jira/Confluence/Bitbucket.
Лёгкий, opinionated, ставка на связку с экосистемой Atlassian.

Сильные стороны:
- Нулевая friction для команд на Atlassian.
- Scorecards, связь с Jira — быстро даёт базовый governance.

Ограничения:
- Самый молодой и узкий из каталогов; вне Atlassian ценность падает.
- Нет ни C4, ни drift, ни глубокого анализа кода.
- Расширяемость слабее Backstage/Port.

Урок для Archon: Compass задаёт планку "минимум каталога, который
ожидает пользователь Jira". Для Archon интеграции с Jira/Confluence
как источники (`sources` + `registry`) важнее, чем конкуренция с
Compass в лоб.

### Structurizr

Что это: инструмент Саймона Брауна для C4. DSL (или код) → диаграммы;
on-prem/cloud; с упором на "architecture as code".

Сильные стороны:
- Лучший DX для C4-as-code, версионирование в Git.
- Лёгкий, понятный, любим архитекторами.

Ограничения:
- Только диаграммы. Нет каталога, нет извлечения фактов из кода,
  нет drift, нет governance. Диаграммы живут отдельно от системы.
- Требует ручной поддержки DSL — то, что Archon хочет автоматизировать
  (`extract` + `reconcile` + `model → portal`).

Урок для Archon: Structurizr — формат/нотация, а не конкурент.
`model` Archon должен уметь экспортировать в Structurizr DSL / LikeC4
(как уже делает прототип `archmap`), а не спорить с ним.

### IcePanel

Что это: SaaS-диаграммирование C4 в браузере, коллаборация, версионирование,
импорт из кода (ограниченно).

Сильные стороны:
- Самый приятный UX для C4 среди SaaS-альтернатив.
- Приближает диаграммы к реальности (импорт, связи).

Ограничения:
- SaaS, остаётся инструментом рисования, пусть и умным.
- Нет knowledge graph, нет policies/drift/assurance, нет PR-гейта.
- Модель — картинка, а не граф фактов.

Урок для Archon: IcePanel задаёт планку визуализации для `portal`.
Но Archon не про рисование — про то, чтобы диаграмма перестала быть
картинкой и стала проекцией `model`.

### Остальные (кратко)

- **Cortex** — близок к OpsLevel/Port (SaaS IDP + scorecards), та же
  ниша каталог-governance, без drift доки-код.
- **Swimm** — drift документации, но на уровне "код ↔ его доки"
  (snippet sync), без архитектурного графа иgovernance.
- **LeanIX / SAP LeanIX** — EA-платформа (enterprise architecture),
  каталог приложений/капабилити, без связи с кодом и без drift.
- **Atlassian Rovo / AI-ассистенты** — чат над Confluence/Jira, но без
  архитектурного графа и без гарантий provenance.

## Где Archon уникален

Ни один из рассмотренных продуктов не закрывает связку целиком:

```
код + доки --extract/interpret--> reconcile --model--> policies/drift
                                              --assurance--> portal/pr-bot/chat-bot/export
```

Конкуренты покрывают фрагменты:
- каталог — все IDP;
- C4 — Structurizr, IcePanel;
- governance/scorecards — Port, OpsLevel;
- drift на уровне проверок — Port/OpsLevel;
- документация рядом с кодом — Backstage TechDocs, Swimm.

Пробел, в который идёт Archon — автоматический, объяснимый drift
между документами и кодом на уровне архитектуры (сервисы, зависимости,
контракты), с жизненным циклом находки и гейтом в PR. Это не "ещё
один каталог".

## Риски и что проверить руками

1. **Цены и лицензии** — все цифры в таблице и тексте требуют ручной
   проверки. SaaS-прайсы меняются часто; OSS-лицензии (Backstage —
   Apache 2.0, Structurizr — Apache 2.0 / коммерческие расширения)
   проверить по репозиториям.
2. **Roadmap 2025-2026** — у Port/OpsLevel/Compass мог появиться
   AI-слой поверх графа. Проверить релиз-ноуты: не закрыли ли они
   часть drift кейсов LLM-сверкой.
3. **On-prem спрос** — ключевой дифференциатор Archon. Валидировать
   интервью (вопрос для user research): насколько критичен on-prem /
   air-gapped для целевых клиентов.
4. **Backstage TechInsights vs Archon policies** — не переоценить
   разрыв: TechInsights уже умеет часть структурных проверок. Нужен
   hands-on тест TechInsights на тех же репо, где будет `policies`.
5. **Swimm** — ближайший по формулировке "docs drift". Разобрать
   детально, чтобы чётко артикулировать разницу (уровень сниппета
   vs уровень архитектуры).

## Выводы для архитектуры Archon

- `registry` + `sources` — делать совместимыми с Backstage
  catalog-info и Port blueprints на входе (миграция без переписывания
  YAML). Это снижает барьер внедрения.
- `model` — внешний контракт: экспорт в Structurizr DSL / LikeC4
  обязателен с MVP (прототип `archmap` уже это делает).
- `policies` — не повторять TechInsights/scorecards 1:1, а бить в
  структурные аномалии графа (циклы, shared DB, нарушение слоёв),
  где у конкурентов пусто.
- `drift` — главный нарратив; требует демо "доки врут — вот пруф из
  кода" на первой же пилотной кодовой базе.
- `assurance` — жизненный цикл находки (в т.ч. accepted-risk) — то,
  чего нет ни у кого из IDP в явном виде; не упрощать до "галочки".
- `pr-bot` — отдельный модуль оправдан: ни один IDP не даёт гейт
  в PR из коробки на уровне архитектуры.
- `chat-bot` — не делать "ещё один чат над Confluence"; чат ценен
  только как интерфейс к `model` с provenance (ответ со ссылкой на
  узел/ребро графа и источник факта).
