# Adversarial review декомпозиции

Метод: каждую границу и каждый модуль пытаемся сломать конкретным сценарием или
вопросом, на который декомпозиция не отвечает. Основание — реестр модулей
(`../architecture/modules/README.md`) и находки F1-F9 из
[`user-journeys.md`](user-journeys.md).

Статус: выводы команды, не финальное решение. Рекомендации в конце требуют
решения (ADR).

Вердикты:
- `hold` — граница выдержала атаку
- `weak` — граница размыта, лечится уточнением
- `broken` — модуль или концепт нужен, но его нет в декомпозиции

---

## Атака 1. `m2` как заложник нерешённого вопроса

`m2 graph` назван ядром, все модули в него упираются. Но OQ-2 (source of truth:
git vs БД vs гибрид) не решён.

Проверим: если ответ — (a) git-as-truth, то у `m2` остаётся merge engine,
версионирование и индекс для запросов. Хранение узлов уходит в git-файлы. Ядро
превращается в производный индекс: критичность та же, но природа другая — ближе
к инфраструктурному слою, чем к "модели продукта".

Вывод: **weak**. Не сломано, но наше "ядро" — самый хрупкий узел, потому что его
содержание определяется вопросом, на который ответа нет. При этом это
единственный модуль, где недопустима переделка после начала кода.

Действие: OQ-2 остаётся блок-вопросом №1. Дополнительно: до его решения не
принимать ничего из `m2` в код, включая схему (текущая `data-model.md` — только
мысленный эксперимент).

## Атака 2. `m1` — это два модуля со склейкой посередине

`m1` объявлен как "два контура: LLM-семантический + детерминированный AST".
Сравним их по осям, по которым модуль обязан быть однородным:

| Ось | AST-контур | LLM-контур |
| :--- | :--- | :--- |
| Корректность | точная, детерминированная | вероятностная |
| Стоимость на сервис | ~0 после написания парсера | деньги и latency на каждый прогон |
| Время прогона на 50k LOC | секунды | минуты |
| Обновляемость | по языкам/фреймворкам | по моделям и промптам |
| Владелец | Паша | Миша |
| Причина отказов | не покрыт язык/паттерн | галлюцинация, нерепрезентативный выбор файлов |
| Что даёт | сырьё для `m3` (аномалии!) | смысл, flows, C3, бизнес-слой |

Разные владельцы, разная экономика, разные сбои, разный цикл изменений — под
одним именем. И OQ-4 ("кто побеждает при противоречии") выглядит не внутренним
вопросом `m1`, а симптомом: примирение двух источников — отдельная операция,
у неё нет дома.

Вывод: **broken**. Нужны три сущности вместо одной: детерминированный
экстрактор, интерпретатор (LLM), и слой примирения. Где жить примирению — в
модели (как часть ingest) или отдельно — решение.

Действие: новый OQ-11 (разделить `m1` или нет) — и заметим, что conflict
resolution это не "деталь", а момент, где рождается provenance, нужный и для
`#manual_check`, и для trust model, и для объяснения аномалий в `d3`.

## Атака 3. `m3` и `m4` структурно двойники

Сопоставим форму:

| | `m3` policies | `m4` drift |
| :--- | :--- | :--- |
| Вход | граф | граф + документы |
| Вычисление | правила | сравнение claims с фактами |
| Выход | finding: severity, статус, lifecycle | finding: противоречие, метрика дрейфа |
| Жизненный цикл детекта | detected/accepted/fixed/false_positive | тот же самый |
| Требует принятия риска | да | да (страницу можно признать "намеренно устаревшей") |

Идентичный lifecycle детекта, разные модули, и одна и та же нерешённая проблема
F4 ("где живут accepted risk") у обоих. F4 оказывается не багом границы `m3`/`m2`,
а отсутствующим понятием: **finding как первоклассная сущность** с общим
хранилищем и workflow, которым пользуются обе аналитики.

Вывод: **weak**, но с конкретным следствием. Два варианта:
- (a) слить в `m3 analyze` с двумя семействами правил (структурные /
  документационные);
- (b) оставить разделёнными, но вынести общий слой владения находками — тогда
  принятие риска, false positive и статусы живут в одном месте, а не в двух.

Вариант (b) предпочтительнее: у `m4` своя тяжёлая инфраструктура (индексация,
эмбеддинги, реестр документов), тащить её в один модуль с `m3` — потерять
границу стоимости. Но общий finding-слой вводится.

Действие: новый OQ-12 (где живёт finding и его lifecycle). Это же закрывает F4.

## Атака 4. Ни один модуль не описывает глобальный проход

Вся рамка нарисована как конвейер `e2 -> m1 -> m2 -> ...`, то есть
"один репозиторий -> своя модель". Но ценность продукта лежит в **сшивке между
репозиториями**:

- landscape (C0) — агрегат всех продуктов (в archmap это отдельная ручная сборка);
- склейка shared-сервисов и топиков (OQ-7) — требует одновременно видеть все
  репозитории;
- аномалии типа "цикл между сервисами из трёх разных репо", "two services
  подключаются к одной БД" — не могут быть вычислены на одном репо;
- дедупликация общих инфраструктурных сущностей.

Нигде в декомпозиции нет слоя, который владеет **корпусом** (множество
проанализированных репозиториев как единое целое) и глобальным проходом по нему.
В модели `m2` это неявно, но `m2` описан как хранилище+запросы, а глобальная
склейка — это батч-вычисление, а не запрос.

Вывод: **broken**. Отсутствует слой разрешения сущностей в масштабе корпуса
(identity/resolution). Это ровно то место, где archmap поддался ручному
`shared/externals.c4`, потому что автоматического дома для этой операции не
нашлось.

Действие: ввести модуль (или явно назначить `m2`-подмодуль) "resolve": батч по
корпусу, склейка сущностей, сборка landscape. Новый OQ-13 (форма: отдельный
модуль / часть `m2` / job внутри `m1`). Сильная сторона такого шага: OQ-7
("как склеивать") перестаёт быть абстрактным и получает владельца.

## Атака 5. У кросс-среза "человек в контуре" есть state и workflow, но нет владельца

Раздел 5 старого документа объявил human-in-the-loop кросс-срезом, не модулем.
Проверим, что он требует на самом деле:

- очередь того, что надо проверить (`#manual_check`, низкий confidence, новые
  аномалии);
- state machine доверия элемента: `auto -> reviewed -> accepted`;
- действие "принять риск" с обоснованием, сроком, владельцем;
- UI этих действий;
- право делать это (RBAC);
- audit-log.

Это данные, workflow и интерфейс. "Кросс-срез" без владельца деградирует в
рассыпанный по `d1`/`m2`/`m3` код, где review-логика дублируется в трёх местах.

Вывод: **broken**. Human-in-the-loop — настоящий модуль (условно `m5 assurance`
или часть finding-слоя из атаки 3). И заметим: это ядро продуктовой идеи
("управляемый контур" как конкурентное преимущество), а не украшение.

Действие: новый OQ-14. Связано с OQ-12 — скорее всего finding-lifecycle и
review-workflow это один модуль.

## Атака 6. Кто-то должен решать, что и когда анализировать (и сколько это стоит)

В архимапе оркестрация живёт в n8n. В нашей декомпозиции оркестрации нет:
`e2` получает webhooks, `m1` "как-то запускается".

Вопросы без дома: очередь задач, приоритеты, ретраи, partial-failure одного
репо в корпусе, throttling LLM, бюджеты на прогон, деградация при нехватке
квоты модели, backfill новых репозиториев, стоимость на tenant (для тарификации
и для защиты от одного жадного клиента).

Для продукта с LLM в контуре стоимость — не деталь эксплуатации, а параметр
модели монетизации (пре-ресерч: open-core / SaaS / enterprise license).

Вывод: **broken**. Отсутствует слой `runtime`/`orchestration` + бюджетирование.
Действие: OQ-15. Плюс NFR-требование, которого в `nfr/` нет: потолок стоимости
на один прогон и на tenant в месяц.

## Атака 7. Нет домена "что мы вообще знаем и про кого" (tenant config)

Клиент устанавливает Archon и должен сказать: вот 40 репозиториев, вот карта
команд, вот какие сервисы относятся к какому продукту, вот наш словарь тегов
(OQ-9), вот наши правила (`m3`), вот какие репо читаем, а вот эти игнорируем.

Кто это хранит? `e1` — про auth/RBAC, не про конфигурацию. `e2` — про доступ к
внешнему миру. Ни один модуль не владеет **описанием самого клиента**. Без него
невозможны ни landscape (нужна привязка сервис -> продукт), ни нормальный
Passport (нужна привязка сервиса к Jira-команде), ни словарь тегов.

Вывод: **broken**. Нужен модуль конфигурации (условно `registry` /
`workspace`): реестр репозиториев, привязки (repo -> product -> team), словарь,
наборы правил, скоуп. Это же естественный владелец OQ-9.

Действие: OQ-16, и вероятное слияние с `e2` в один слой "корпус и доступ к
нему" (см. рекомендацию).

## Атака 8. `d1 portal` vs `d2 catalog` — не граница, а одна сущность

Мы пытаемся провести линию между "портал" и "каталог". Но каталог без портала не
существует: карточка сервиса — это экран портала. Проверка из F1 не дала
критерия разделения, потому что его нет: `d2` не имеет ни своих данных, ни своего
интерфейса к `m2`, отличного от `d1`.

Вывод: `d2` **слабый модуль**, скорее секция `d1`, чем самостоятельная единица.
Единственная причина сохранить отдельный код — если каталог переиспользуется
вне портала (например, как сервис-реестр для внешних систем через API). Тогда он
должен быть не каналом, а API над `m2`, а портал — его потребителем.

Действие: OQ-17 (каталог: секция UI или публичный API сервис-реестра?). От ответа
зависит, `d2` = канал, `d2` = API или `d2` = ничего.

## Атака 9. Каналы доставки не имеют общего основания

`d1`, `d3`, `d4`, и потенциально экспорт-отчёты (F7) — все рисуют фрагменты
графа, все требуют auth-контекст, все страдают от отсутствия deep link (F2).
Общего слоя нет, значит каждая доставка реализует своё.

Вывод: **weak**. Это не дыра декомпозиции, а сигнал: `m2` query API должен быть
спроектирован как **единый контракт для всех каналов**, с сериализацией
фрагментов графа в форму, пригодную и для web-рендера, и для комментария в MR, и
для ответа в чате. Если API не выдержит четыре канала одновременно — API плохой.

Действие: требование к ADR на query API (`m2`), отдельно зафиксировать
"мультимодальный" выход (структура + текст + короткая ссылка).

## Атака 10. `e2` — модуль или набор плагинов?

Коннектор Git — это не архитектура, это драйвер. Если `e2` = 10 модулей по
количеству провайдеров, декомпозиция его не описывает; если `e2` = интерфейс
коннектора + N реализаций, то модуль описан неверно (он описывает механизм, а не
ответственность).

Плюс: где граница `e2` / `m4`? Confluence-документы надо не только прочитать
(`e2`), но и нарезать, проэмбеддить, завести в реестр (`m4`). Сейчас непонятно,
кто где заканчивается.

Вывод: **weak**, лечится формулировкой: `e2` = транспорт и аутентификация,
всегда возвращает "сырые артефакты + события"; нормализация в доменную модель —
на потребителе (`m4` для документов, `m1` для кода).

## Атака 11. Декомпозиция из 10 модулей для команды из 4 человек

Логическая декомпозиция не равна физическому разделению (это и есть OQ-8). Но
у нас в файлах модулей границы уже читаются как "это разные сервисы". Проверка:
команда, которая может одновременно держать 10 интерфейсов, 10 владельцев, 10
контрактов? Нет.

Вывод: **weak по форме подачи**, не по сути. Нужна явная пара: *логические
модули* (для понимания и контрактов) vs *сборочные единицы* (что реально
разворачивается и кто пишет). MVP обязан собираться из 2-3 единиц, иначе команда
утонет в интеграциях.

Действие: внести различие в правила реестра, держать в OQ-8.

## Атака 12. Модель данных против модулей (проверка на согласованность)

`data-model.md` содержит сущности, у которых нет владельца в декомпозиции:
`Risk Status` (атака 3/5), `Landscape` (атака 4), `Specification` и её реестр
(F5: дубль с `m4`), `Drift` (нет модуля-drift-сущности, `m4` её только
вычисляет). И наоборот: `m2` объявлен владельцем `Contract`, но `Contract` как
контракт между сервисами может быть валидирован только при склейке (атака 4).

Вывод: **weak**. Модель данных написана до того, как появились владельцы, и
часть сущностей теперь сироты. Требуется проход "каждая сущность -> модуль-
владелец" (полезно как отдельный артефакт, снимает 80% будущих споров).

## Рекомендуемая ревизия декомпозиции

Не финал, а кандидат для обсуждения. Слева — было, справа — что предлагает
атака:

| Слой | Кандидат |
| :--- | :--- |
| Корпус | `registry` (конфигурация: репо, привязки, словарь, скоуп) + `sources` (транспорт/коннекторы) |
| Извлечение | `extract` (детерминированный, AST/манифесты) и `interpret` (LLM-семантика) |
| Примирение | `reconcile` — споры источников, provenance, confidence, `#manual_check` |
| Модель | `model` (graph): хранение, версии, merge с ручными правками, query API |
| Глобальное | `resolve`: склейка сущностей по корпусу, сборка landscape |
| Аналитика | `analyze`: два семейства — правила (`policies`) и дрейф (`drift`) |
| Находки и доверие | `assurance`: lifecycle находок, ревью, принятие риска, trust-статы |
| Доставка | `portal` (включая catalog-секции), `pr-bot`, `chat-bot`, `export` |
| Рантайм | `runtime`: очереди, планирование, ретраи, бюджеты LLM |
| Платформа | `platform`: SSO, RBAC, audit, tenancy, секреты |

Что это меняет содержательно:

1. Появляется дом для OQ-7 (`resolve`) — самый сложный алгоритмический вопрос
   продукта перестаёт быть приписанным "графу вообще".
2. Разделяется то, у чего разная экономика (`extract` дешёвый и точный против
   `interpret` дорогой и вероятностный) — это напрямую влияет на OQ-15.
3. Принятие риска и ревью получают владельца, а не расползаются по UI.
4. `m1` как "модуль Дениса+Паши+Миши" распадается на три, у каждого один
   ответственный — снимает организационный конфликт, который был зашит в
   декомпозицию.
5. Доставка перестаёт претендовать на симметрию: каталог = секция или API,
   экспорт = канал (закрывает F7).

Цена ревизии: переименование кодов (`m1..m4` -> новые), правки реестра и всех
файлов модулей. Небольшая сейчас, дорогая после начала кода.
