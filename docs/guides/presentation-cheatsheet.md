# Шпаргалка для презентации Archon

## 30 секунд

Archon — платформа, которая сама читает код и документы и говорит, где они не совпадают. Миссия — **Zero Drift** (документы не расходятся с кодом). Можно настроить, чтобы PR не мержился, пока документы не обновлены. Такого решения сейчас нет на рынке.

## Что видит пользователь (4 точки входа)

Внутри 16 модулей, но пользователь видит только 4 интерфейса:

- **Портал (веб)** — диаграммы, список сервисов, список проблем ("здесь код не совпадает с документом"), оценка зрелости.
- **Бот в Git** — комментирует PR: "Ты изменил код, обнови документ `docs/payments.md`". Можно настроить блокировку мержа.
- **Чат-бот** — отвечает на вопросы типа "кто владелец сервиса платежей?" со ссылкой на код.
- **Экспорт** — выгружает отчёт на дату для аудита (PDF/JSON) вместо ручных скриншотов.

Всё остальное — невидимая "фабрика", которая это делает. Подробнее — `architecture/product-overview.md`.

## 5 блоков (как объяснять устройство)

Для презентации группируй 16 модулей по близости к пользователю:

| Блок | Что делает | Пример |
| :--- | :--- | :--- |
| Витрина | Показывает результат там, где удобно | Портал, бот в Git, чат-бот, экспорт |
| Решение | Следит за статусом каждой проблемы | "Обнаружена → исправлена / риск принят / ложная тревога" |
| Мозг | Строит граф из кода и документов, ищет проблемы | Граф связей, поиск противоречий |
| Фабрика | Читает код, документы, разбирается в конфликтах | Парсеры кода, LLM для понимания смысла |
| Фундамент | Очереди, права, аудит (без этого не продать) | SSO, планирование задач, бюджеты LLM |

**Для MVP:** витрина = портал + бот в Git, главная фича — "доки врут, вот доказательство из кода".

## Как это работает (если спросят технические детали)

Короткий ответ: система читает код → строит граф связей → сверяет с документами → находит расхождения → показывает пользователю.

Полная схема потока данных в `modules/README.md`.

## Что изменилось в последней версии декомпозиции (ADR-0004)

Было 10 модулей с буквами → стало 16 плоских модулей. Ключевые изменения:
- Отдельный модуль для разрешения конфликтов между источниками (`reconcile`).
- Разделили "что анализировать" (`registry`) и "как подключиться к источникам" (`sources`).
- Единый контур для управления проблемами (`assurance`).

## Что уже есть на рынке (конкуренты)

- **Backstage** — каталог сервисов, но не проверяет drift (расхождение с кодом). Это фреймворк, нужна команда для поддержки.
- **Port/OpsLevel** — SaaS для скоркардов. Проверяют правила, но не сравнивают документы с кодом. Нет on-premise.
- **Compass** — лёгкий каталог от Atlassian. Полезен только если вся компания в Atlassian.
- **Structurizr/IcePanel** — лучшие редакторы C4-диаграмм. Но это картинки, нарисованные руками, не граф из кода.
- **Swimm** — самый близкий по идее "документы против кода", но работает на уровне сниппетов, а не архитектуры.

**Наша ниша:** мы не просто каталог. Мы автоматически сверяем документы с кодом на уровне архитектуры и блокируем мерж, пока не исправлено. Этого не делает никто.

## Риски (если спросят "а что может пойти не так")

- Анализ конкурентов — черновик, цены/релизы не проверены с их сайтов.
- Сценарии использования писал один человек — нужна внешняя проверка (интервью с реальными пользователями).
- Есть 3 открытых вопроса (OQ-1, OQ-2, OQ-8), которые блокируют код. Пока они не решены — код не пишем.

## Ожидаемые вопросы

**"Почему не сделать плагин к Backstage?"**
Наша главная ценность — движок, который читает код и сверяет с документами. Портал совместим с форматом Backstage — мы не конкурируем, а дополняем.

**"Зачем два способа читать код (extract и interpret)?"**
`extract` — точно и дешево (парсит синтаксис). `interpret` — понимает смысл через LLM, но дорого и может ошибаться. Если смешать — не поймёшь, где факт, а где предположение.

**"Кто владелец модуля?"**
Никто. Модули — это архитектура, а не зоны ответственности людей. Задача может затрагивать несколько модулей. Владелец есть у задачи, не у модуля.

**"Когда начнёте писать код?"**
После того, как закроем 3 блокирующих вопроса (судьба прототипа, где хранить модель, как разворачивать систему).
