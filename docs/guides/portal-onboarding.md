# Archon Portal: спецификация скоупа и онбординг команды разработки

Документ определяет архитектурный контекст, границы ответственности, технологический стек и функциональный скоуп для разработки клиентской витрины `archon-portal`.

---

## 1. Контекст продукта Archon

Archon — enterprise-платформа docs-as-code и AI-native Source of Truth.

В распределенных системах документация быстро устаревает: ручные схемы в Confluence/Miro не соответствуют актуальному коду, а AI-ассистенты (Cursor, Copilot) галлюцинируют из-за отсутствия верифицированного контекста.

Платформа решает проблему расхождения (Spec-Drift):
1. Сканирует Git-репозитории;
2. Детерминированно извлекает факты из синтаксиса кода (AST-анализ) и извлекает семантику из документации через LLM;
3. Строит единый граф сущностей (микросервисы, базы данных, очереди, внешние API) в PostgreSQL + Apache AGE;
4. Выявляет расхождения между кодом и документацией, формируя доказательную базу с точными строками и цитатами.

## 2. Глоссарий терминов, концепций и подходов

Для разработки интерфейса важно понимать предметную область продукта и его базовые концепции:

### Docs-as-Code и Zero Drift (Нулевой дрейф)
* **Docs-as-Code:** подход, при котором документация пишется, хранится и версионируется так же, как исходный код (в Git, в текстовых форматах Markdown/DSL, с проверками в CI/CD).
* **Spec-Drift (Архитектурный дрейф / рассинхрон):** расхождение между реальным кодом и проектной документацией. Код меняется ежедневно, а схемы устаревают.
* **Zero Drift:** целевое состояние платформы — состояние, при котором документация автоматически верифицируется против кодовой базы и не расходится с ней.

### Модель C4 и LikeC4
* **Модель C4 (Context, Containers, Components, Code):** иерархический подход к описанию архитектуры программных систем (автор — Саймон Браун). Вместо одной перегруженной схемы система представляется в 4 масштабах:
  1. *Context (Системный контекст):* система как черный ящик среди пользователей и внешних систем;
  2. *Container (Контейнеры/Сервисы):* микросервисы, базы данных, очереди, веб-приложения;
  3. *Component (Компоненты):* внутренние модули и контроллеры конкретного сервиса;
  4. *Code (Код):* классы, методы и функции.
* **LikeC4:** современный декларативный язык (DSL) и визуальный движок для C4-моделей. Позволяет интерактивно проваливаться внутрь сервисов (zoom-in) и переходить между уровнями абстракции прямо в браузере.

### Извлечение фактов: AST vs LLM
* **Детерминированное извлечение (AST — Abstract Syntax Tree):** модуль `extract` разбирает синтаксические деревья кода (парсеры вроде Tree-sitter). Это дает 100% точность, высокую скорость и отсутствие галлюцинаций. Так извлекаются роуты, импорты, SQL-запросы, вызовы HTTP-клиентов.
* **Семантическое извлечение (LLM):** модуль `interpret` использует языковые модели для понимания текстовых описаний, комментариев и документов архитектуры.
* **Reconcile (Примирение) и Матрица доверия:** если код (AST) утверждает одно (сервис А вызывает сервис Б по эндпоинту `/v2/pay`), а документация (LLM) утверждает другое (`/v1/pay`), то код всегда приоритетнее (AST > LLM). Факт конфликта фиксируется как расхождение.

### Доказательная база (Evidence-first) и Провенанс (Provenance)
* **Провенанс (Provenance):** цепочка происхождения каждого факта в графе. Система всегда знает, откуда взят факт (номер коммита, парсер, время).
* **Evidence Files:** координатная привязка к исходному коду (путь к файлу и точный диапазон строк, например `src/billing/client.py#L42-L48`). В UI инбокса доказательства показываются инженеру как подтверждение найденной проблемы.

### Жизненный цикл находок (Assurance) и Human-in-the-Loop
* **Finding (Находка):** зарегистрированное расхождение или нарушение архитектурного правила.
* **Human-in-the-loop:** автоматика находит проблемы, но решения принимает человек. У проблемы есть статусы:
  * *New / Detected:* только что обнаружена;
  * *Confirmed:* инженер подтвердил, заведен баг;
  * *Risk Accepted:* архитектурный совет временно разрешил отклонение от правил;
  * *False Positive:* ложное срабатывание анализатора.

### AI-native Source of Truth и MCP
* **AI-native Source of Truth:** единый канонический граф архитектуры всей компании, хранящийся в БД (PostgreSQL + Apache AGE).
* **MCP (Model Context Protocol):** открытый стандарт (JSON-RPC), позволяющий AI-агентам в IDE (Cursor, Claude Code, Copilot) подключаться к Archon и получать верифицированный контекст архитектуры, чтобы не галлюцинировать при генерации кода.

## 4. Роль сборочной единицы `archon-portal`

В соответствии с физической топологией ([ADR-0007](../adr/0007-saas-process-topology-and-packaging.md), [deployment.md](../architecture/deployment.md)) система собирается из 3 процессов:
* `archon-core-service` (Kotlin / JVM) — инженерное ядро, граф, база данных, REST API;
* `archon-ai-service` (Python) — LLM-пайплайны, RAG, MCP-сервер;
* `archon-portal` (TypeScript / React) — статическое SPA-приложение.

`archon-portal` — единственная визуальная витрина системы для инженеров, тимлидов и архитекторов. Приложение не хранит собственных данных и работает как тонкий клиент поверх REST API ядра.

## 5. Распределение ролей в паре разработчиков

Разработка ведется в едином репозитории клиентского приложения с четким разграничением зон ответственности:

### Разработчик 1: Frontend Lead
* Проектирование компонентов UI и дизайн-системы.
* Верстка страниц: Каталог, Паспорт сервиса, Инбокс находок.
* Клиентский роутинг, навигация, адаптивность.
* Состояния загрузки (skeletons), обработка ошибок и пользовательские сценарии подтверждения действий.

### Разработчик 2: Fullstack / Client Data & Integration Lead
* **Слой данных и моки:** настройка Mock Service Worker (MSW) или локального mock-сервера с фикстурами. Обеспечивает возможность независимой разработки интерфейса до готовности бэкенда ядра.
* **Интеграция графа LikeC4:** подключение пакета `@likec4/diagrams`, преобразование данных из API в формат C4-модели, обработка событий выбора узлов и зума, экспорт схем в PNG/SVG.
* **Сетевой клиент:** генерация TypeScript-типов из OpenAPI-спецификации, настройка кэширования и мутаций через TanStack Query.
* **Инфраструктура поставки:** написание `Dockerfile` (сборка статики и раздача через Nginx), конфигурация переменных окружения (`VITE_API_URL`).

## 6. Функциональный скоуп (3 ключевых блока)

### Блок 1. Каталог сервисов и Паспорт сервиса ([modules/portal.md](../architecture/modules/portal.md))
* **Каталог (Service Catalog):**
  * Таблица микросервисов организации с поиском по названию.
  * Фильтрация по владельцам (командам), языкам программирования, наличию обнаруженного дрейфа.
  * Индикаторы архитектурного статуса сервиса.
* **Паспорт сервиса (Service Passport):**
  * Карточка метаданных: имя, репозиторий, стек, команда-владелец.
  * Топологические связи: входящие вызовы, исходящие зависимости, используемые хранилища (БД, топики Kafka/RabbitMQ).
  * Реестр документированных эндпоинтов (REST/gRPC контракты).

### Блок 2. Инбокс расхождений и рисков (Assurance Inbox)
* Список зарегистрированных аномалий и расхождений из модуля `assurance`.
* Карточка доказательной базы (Evidence Review):
  * Фрагмент документации с цитатой требования;
  * Фрагмент кода с указанием файла и диапазона строк (`evidence_files`);
  * Описание расхождения.
* Интерфейс фиксации решений инженера:
  * Подтвердить дефект (требуется исправление кода или документации);
  * Принять архитектурный риск (Risk Accepted);
  * Отклонить как ложную тревогу (False Positive).

### Блок 3. Интерактивная архитектурная карта (LikeC4 Architecture Viewer)
* Встраивание интерактивного компонента диаграмм на базе библиотеки `@likec4/diagrams`.
* Иерархическая навигация по уровням абстракции: System Context -> Container -> Component.
* Интерактивность: панорамирование, масштабирование, клик по узлу с переходом в Паспорт сервиса.

## 7. Технологический стек

* **Среда сборки:** Node.js 20+, Vite, TypeScript.
* **UI-библиотека:** React 18+.
* **Стилизация:** Tailwind CSS.
* **Компонентная база:** `shadcn/ui` (нейтральная темная инженерная палитра).
* **Управление серверным состоянием:** `@tanstack/react-query`.
* **Табличные компоненты:** `@tanstack/react-table`.
* **Рендеринг C4-схем:** `@likec4/diagrams`, `@likec4/core`.
* **Иконки:** `lucide-react`.

## 8. Принцип автономной разработки (Mock-First)

Разработчикам портала **не требуется** запускать инфраструктуру ядра (PostgreSQL, Apache AGE, Temporal, LLM).

1. Архитекторы проекта предоставляют OpenAPI/Swagger спецификацию со схемами DTO.
2. В репозитории портала настраивается MSW (Mock Service Worker) или легковесный mock-сервер, отдающий валидные синтетические ответы.
3. Разработка и тестирование UI проводятся на моках.
4. Переключение на production-бэкенд выполняется изменением базового URL в конфигурации Vite.

## 9. Этапы разработки и критерии готовности (DoD)

1. **Этап 1 (Каркас и моки):**
   * Репозиторий инициализирован: Vite, TypeScript, Tailwind CSS, базовые компоненты `shadcn/ui`.
   * Настроен слой мок-данных (MSW) с фикстурами сервисов и находок.
2. **Этап 2 (Таблицы и инбокс):**
   * Реализован Каталог сервисов и Паспорт сервиса.
   * Реализован Инбокс находок с модальным окном просмотра доказательств (evidence).
3. **Этап 3 (Граф LikeC4):**
   * Подключен `@likec4/diagrams`.
   * Схема рендерится из структуры данных и поддерживает клики по узлам.
4. **Этап 4 (Упаковка):**
   * Настроен `Dockerfile` с многоэтапной сборкой (Node.js build -> Nginx alpine).
   * Проверено отсутствие ошибок типизации (`tsc --noEmit`) и сборки бандла (`npm run build`).
