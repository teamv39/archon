# Гайд для тимлида: как вести Archon на GitHub

Для Дениса. Команда 4 человека + будет расти. Вся работа — в GitHub.

**Цель:** сэкономить твоё время как лида, не утонуть в процессах.

## Главный принцип

GitHub — операционная система проекта. Если чего-то нет в Issues/Projects/ADR — этого не существует. Синхроны и чаты — для обсуждений, а не для хранения решений.

## 1. Настройка GitHub (делается один раз)

### Защита основной ветки

Сейчас можно пушить в `main` — пока строим базу, это нормально (твоё решение). Но уже сейчас подготовь защиту:

1. Иди в `Settings → Branches → Add rule` для ветки `main`
2. Поставь галочку "Require pull request before merging" — **пока выключено**
3. Включишь, когда скажешь "хватит, теперь только через PR"
4. "Do not allow bypass" — для всех кроме тебя (на переходный период)

### CODEOWNERS (кто должен ревьюить что)

Создай файл `/.github/CODEOWNERS`:
```
/docs/adr/ @shteppinson
/docs/architecture/ @shteppinson
```

Теперь любое изменение в ADR не смержится без твоего аппрува. Остальное может ревьюить любой.

### GitHub Projects (один проект на всё)

Не делай отдельный проект на каждый модуль. Один проект `Archon`, внутри — разные представления (views).

**Поля (custom fields):**

| Поле | Тип | Варианты |
| :--- | :--- | :--- |
| Status | Status | Todo / In Progress / In Review / Done |
| Module | Select | 16 модулей + `cross-cutting` + `research` |
| Type | Select | `feature` / `research` / `adr` / `docs` / `tech-debt` / `bug` |
| Size | Select | `S` (1-2 дня) / `M` (3-5 дней) / `L` (1-2 недели) / `XL` (эпик, надо резать) |
| Priority | Select | `P0` (блокер) / `P1` (сейчас) / `P2` (потом) / `P3` (идея) |
| OQ | Text | ссылка на OQ-*, если задача закрывает вопрос |

**Представления (Views):**

1. **Board** — по Status. Смотришь каждый день.
2. **By Module** — группировка по Module. Видишь, где затор.
3. **Roadmap** — по Milestone/Iteration. Для планирования.
4. **My Work** — фильтр `assignee:@me`. Каждый видит своё.

### Labels (минимальный набор)

Не плоди 20 лейблов. Достаточно:

- `type: feature` / `research` / `adr` / `docs` / `tech-debt` / `bug`
- `priority: P0` / `P1` / `P2`
- `module: <имя>` — только если задача про один модуль (часто задачи `cross-cutting`)
- `blocked` — ждёт решения OQ/ADR или внешнего блокера

Всё остальное — через поля проекта, не лейблы.

### Milestones (по фазам из ROADMAP)

- `Phase 1: Research & Foundation` (сейчас)
- `Phase 2: MVP`
- `Phase 3: ...`

Milestone = проверяемый результат ("закрыты OQ-1/2/8, есть черновик data-model"), а не "сделали модуль X".

## 2. Как резать работу (чтобы 4 человека не мешали друг другу)

### Правило декомпозиции

16 модулей — это архитектура, не план работ. Задачу режешь так:

- **Вертикальный слайс > горизонтальный слой.** 
  Лучше: "drift для одного типа документа на одном репо end-to-end (грязно, но работает)"
  Хуже: "идеальный extract для всех языков, но без drift"
  
- **Размер — S/M.** Если задача L/XL — это эпик, режь. 
  Критерий: можно ли сделать PR за 2-3 дня? Если нет — режь.
  
- **Нет владельца модуля — есть владелец задачи.** 
  В issue — один assignee. Если работают двое — одна задача, один assignee, второй в reviewers. Иначе никто не отвечает.

### Шаблоны Issue

Заведи `/.github/ISSUE_TEMPLATE/` — три шаблона:

**feature.md:**
```markdown
## Зачем (1 предложение)
## Что сделать (чек-лист)
- [ ]
## Критерий готовности
## Связи
- OQ: 
- ADR: 
- Модули: 
```

**research.md:**
```markdown
## Вопрос
## Как проверяем (метод)
## Ожидаемый результат (документ/PR/решение)
## Дедлайн (исследования без дедлайна гниют)
```

**adr.md:**
```markdown
## Вопрос (OQ-*)
## Варианты (2-3, с плюсами/минусами)
## Рекомендация автора
## Кто решает + дедлайн
```

### Как раздавать задачи

- **Ты** — держишь OQ и ADR (решаешь или назначаешь того, кто решает).
- **Остальные** — берут задачи из `Todo` сами (pull, не push). 
  Твоя работа — чтобы в `Todo` всегда было 1.5× задач на человека, приоритизированных.
- **Раз в неделю** — груминг на 30 мин: проходите `Todo`, выкидываете мусор, режете XL, уточняете критерии готовности.

## 3. Workflow (два режима)

### Сейчас (фаза базы, можно в main)

- Пуш в `main` разрешён, но каждый пуш — маленький и с понятным сообщением.
- Документация и код в одном PR/коммите — правило из DEVELOPMENT.md.
- ADR — всегда через PR, даже сейчас. Архитектурные решения без ревью не живут.

### Потом (когда скажешь "теперь по-взрослому")

- Включаешь branch protection на `main`.
- Ветки: `feature/ARCH-123-kebab` от `main` (пока без `develop` — он нужен только когда появится релизный цикл).
- PR: 1 аппрув + CI green. Ты — codeowner для `/docs/adr/` и `/docs/architecture/`.
- Squash-merge, сообщение по формату `ARCH-123: что сделано`.

**Переход** — одним объявлением в чате + включением правила. Не тяни дольше Phase 1.

## 4. ADR и открытые вопросы (твой главный инструмент)

- **OQ** (`docs/architecture/open-questions.md`) — бэклог решений. Каждый OQ — это issue с лейблом `adr`. Без issue OQ невидим.
- **ADR** (`docs/adr/`) — принятое решение. Пишет автор, решает ты (или назначенный). Формат: контекст → варианты → решение → последствия.
- **Правило:** код, который зависит от открытого OQ, не пишется. Сначала ADR, потом код. Исключение — прототип с пометкой `spike:` в названии ветки/PR, который потом выкинут.

**Сейчас блокеры для кода:** OQ-1 (судьба archmap), OQ-2 (где хранить модель), OQ-8 (топология). Твоя ближайшая работа как лида — закрыть их в ADR-0002/0003.

## 5. Ритуалы (минимум на 4 человека)

| Ритуал | Когда | Сколько | Что |
| :--- | :--- | :--- | :--- |
| **Daily** | каждый день | 10 мин | Асинхронно в GitHub Discussions или треде: вчера/сегодня/блокер. Синхрон только если есть блокер. |
| **Груминг** | 1 раз в неделю | 30 мин | Проход по Project Todo, приоритизация, нарезка больших задач |
| **Демо** | 1 раз в 2 недели | 30 мин | Показываете работающую фичу, не слайды. Даже если грязно. |
| **Ретро** | 1 раз в 2 недели | 30 мин | Что мешало → одно действие на следующую итерацию. Не больше. |

**Не вводи** стендапы на 30 мин и планирования на 2 часа. На 4 человек это убивает скорость.

## 6. Как растить команду и делить на подкоманды

**Не дели по модулям.** Дели по потокам (направлениям):

- **Поток 1: Корпус + Извлечение** — `registry/sources/extract/interpret/reconcile`
- **Поток 2: Модель + Аналитика** — `model/resolve/policies/drift`
- **Поток 3: Доверие + Доставка** — `assurance/portal/pr-bot/chat-bot/export`
- **Поток 4: Инфра** — `runtime/platform` (часто один человек на два потока)

Когда будет 6-8 человек — два потока по 3-4 человека. Когда 10+ — три потока.

**Правило подкоманды:** у неё есть бэклог (фильтр по Module в Projects) и владелец потока (не владелец модулей, а ответственный за движение). Архитектурные решения всё равно через общий ADR.

## 7. Качество без бюрократии

- **CI сейчас:** хотя бы `markdownlint` + проверка битых ссылок в docs. Подключишь за час, ловит 80% мусора.
- **CI потом:** тесты, линтеры — по мере появления кода. Не ставь CI ради CI до первого кода.
- **Definition of Done (когда задача готова):**
  - [ ] PR/пуш смержен
  - [ ] Документация обновлена (если менялась архитектура — ADR/OQ)
  - [ ] Связанная OQ помечена (если закрыта)
  - [ ] В Projects статус `Done`

## 8. Твои еженедельные чек-листы

**Понедельник (15 мин):**
- [ ] В `Todo` есть задачи на неделю для каждого?
- [ ] Есть ли `blocked` задачи, которые ты можешь разблокировать (принять ADR, ответить)?
- [ ] Один приоритет на неделю сформулирован одним предложением?

**Пятница (15 мин):**
- [ ] Что в `Done` — совпадает с планом?
- [ ] Что переехало — почему? Резать мельче или приоритет не тот?
- [ ] Нужно ли новое ADR на следующую неделю?

## 9. Анти-паттерны (чего не делать)

- Не заводи `develop` ветку пока нет релизов. Лишняя сложность.
- Не делай `module/*` ветки. Ветка — про задачу, не про модуль.
- Не храни решения в чате/Notion/голове. Если нет в GitHub — нет.
- Не назначай задачу на двоих. Один assignee, второй — reviewer.
- Не держи OQ открытыми месяцами. OQ без дедлайна — это прокрастинация. Ставь дедлайн на решение, даже если перенесёшь.

## 10. Что сделать прямо сейчас (следующие 3 дня)

1. Создать GitHub Project `Archon` с полями выше, завести 4 представления.
2. Завести issue на каждый OQ-1/2/8 с лейблом `adr`, назначить решающего и дедлайн.
3. Нарезать 5-7 задач размера S/M на ближайшую неделю (не модули целиком, а вертикальные слайсы).
4. Завести `/.github/ISSUE_TEMPLATE/` и `CODEOWNERS`.
5. Провести груминг — разложить задачи по приоритетам, чтобы каждый мог взять следующую без тебя.
