# Architecture Decision Records

История всех значимых архитектурных решений в проекте.

## Что фиксировать в ADR

- Выбор технологий (языки, фреймворки, библиотеки, БД)
- Архитектурные паттерны (монолит vs микросервисы, event-driven vs request-response)
- Изменения в структуре системы
- Решения по безопасности и compliance
- Изменения в API контрактах
- Выбор инструментов разработки

## Что НЕ фиксировать в ADR

- Мелкие рефакторинги
- Исправления багов
- Изменения в UI без архитектурного влияния
- Обновления зависимостей без смены подхода

## Формат ADR

Используем упрощенный формат на основе MADR:

```markdown
# NNNN. Название решения

Дата: YYYY-MM-DD

## Статус

[Proposed | Accepted | Deprecated | Superseded by ADR-XXXX]

## Контекст

Какую проблему решаем? Что привело к необходимости принять решение?

## Решение

Что именно делаем?

## Альтернативы

Какие варианты рассматривали? Почему не выбрали их?

## Последствия

Что это решение дает и что усложняет?

### Плюсы
- ...

### Минусы
- ...

### Риски
- ...
```

## Нумерация

ADR нумеруются последовательно с `0001`. Номер не меняется, даже если решение deprecated.

## Изменение решений

Если решение изменилось:
1. Не удаляем старый ADR
2. Меняем статус на `Deprecated` или `Superseded by ADR-XXXX`
3. Создаем новый ADR с новым решением
