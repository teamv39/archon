# 0003. Хранилище Source of Truth и модель изоляции тенантов

Дата: 2026-09-05

## Статус

Accepted (закрывает OQ-2 и OQ-5)

## Контекст

Archon позиционируется как AI-native Source of Truth архитектуры программных систем (ADR-0006). Модуль `model` является центральным хранилищем графа знаний (сервисы, базы данных, очереди, эндпоинты, топики, зависимости).

К графу обращаются:
- **MCP Server** — IDE-агенты запрашивают контекст, зависимости и радиус поражения в реальном времени.
- **Веб-портал** — интерактивная визуализация C1–C3 и dynamic flows в LikeC4.
- **PR-bot и CI/CD** — гейты проверки архитектурных инвариантов и детекция дрейфа.
- **Policy Engine** — поиск архитектурных антипаттернов (shared database, циклические зависимости, прямое обращение в обход API).

Перед проектом стояли два взаимосвязанных вопроса:
1. **OQ-2 (Source of Truth):** Где живет эталонный граф — в Git-файлах, в специализированной графовой БД или в гибридном виде?
2. **OQ-5 и OQ-8 (Хранилище и Мультитенантность):** Какую СУБД использовать для графа в модели Managed SaaS и как гарантировать 100% изоляцию данных корпоративных клиентов?

## Решение

1. **Технологический стек хранилища (PoC и MVP):**
   * В качестве основного хранилища для PoC и MVP принимается **PostgreSQL 16 с расширением Apache AGE** (`apache/age:PG16_latest`).
   * Это позволяет объединить в едином экземпляре/кластере реляционные сущности платформы (пользователи, тенанты, права доступа, аудит, история прогонов) и графовые структуры связей.
   * Исключаются распределенные транзакции (2PC) и рассинхронизация между реляционными метаданными и графом.

2. **Модель мультитенантности (Строгая изоляция данных):**
   * Принята модель: **один тенант (клиент) = один изолированный граф** (`SELECT create_graph('tenant_<id>')`).
   * Под капотом Apache AGE создает для каждого графа выделенную схему PostgreSQL с собственными таблицами узлов (`_ag_label_vertex`) и ребер (`_ag_label_edge`).
   * **Категорически запрещено** смешивание данных разных клиентов в общем графе с фильтрацией по `tenant_id` в запросах. Изоляция обеспечивается на уровне схемы СУБД. Ошибка в прикладном запросе физически не может привести к межклиентской утечке архитектурных данных.
   * Удаление данных клиента выполняется атомарно через `SELECT drop_graph('tenant_<id>', true)`.

3. **Абстракция слоя доступа и стандартизация на openCypher:**
   * Все операции выборки графа, поиска путей, расчета радиуса поражения и проверки архитектурных антипаттернов формулируются строго в стандарте **openCypher**.
   * Доступ к графу инкапсулируется в Data Access Layer (DAL) модуля `model`. В коде графовых запросов запрещается использование специфичных хаков Postgres, не переносимых в другие графовые СУБД.

4. **Стратегия миграции на Enterprise High-Load:**
   * Apache AGE транслирует Cypher-запросы в реляционные Join'ы и B-tree сканы поверх PostgreSQL (отсутствует нативный Index-Free Adjacency). Для сверхвысоких нагрузок (сотни тысяч RPS, обходы глубже 3–4 хопов на миллионных графах) AGE имеет ограничения по производительности и локам при конкурентной записи.
   * Для фазы MVP нагрузка Archon ограничена: граф компании уровня Enterprise ($10^4$–$10^5$ узлов) целиком помещается в RAM / `shared_buffers` ($50$–$200$ МБ), а типичные запросы MCP и портала требуют обхода лишь 1–2 хопов ($1$–$5$ мс).
   * После релиза MVP будет проведено нагрузочное тестирование. При исчерпании лимитов масштабирования Apache AGE будет осуществлен бесшовный переход на специализированную графовую БД (Memgraph или Neo4j). Благодаря стандартизации на openCypher переписывание прикладной логики не потребуется — заменится только транспортный драйвер подключения.

5. **Отношение Git vs Граф:**
   * Исходные репозитории клиентов в Git являются источниками сырых фактов и кода (Source of Code).
   * Граф в Archon является каноническим агрегированным источником правды (Source of Truth) текущего состояния архитектуры.
   * Изменения в коде фиксируются через события коммитов/PR, обрабатываются контуром извлечения (`extract` -> `interpret` -> `reconcile`) и атомарно вливаются в граф тенанта с фиксацией трассировки к файлам-доказательствам (`evidence_files`).

## Альтернативы

1. **Git-first (модель .c4 файлов в Git как единственный SoT):**
   * *Плюсы:* Нативная версионность Git, знакомый flow PR.
   * *Почему отклонено:* Невозможно эффективно выполнять онлайн-запросы радиуса поражения, транзитивных зависимостей и проверки политик в реальном времени для MCP и CI/CD гейтов. Требовало бы парсинга всего набора файлов при каждом запросе агента из IDE.

2. **Выделенная графовая БД (Neo4j / Memgraph) с первого дня:**
   * *Плюсы:* Максимальная производительность на глубоких обходах, нативный Index-Free Adjacency.
   * *Почему отклонено:* Преждевременное усложнение инфраструктуры на этапе MVP. Neo4j имеет жесткую коммерческую лицензию и тяжел в эксплуатации; Memgraph требует отдельного кластера и поддержки распределенной консистентности с реляционной базой тенантов.

3. **Единый общий граф с `tenant_id` в свойствах узлов/ребер:**
   * *Плюсы:* Единый набор таблиц, проще администрировать базу на старте.
   * *Почему отклонено:* Недопустимо для enterprise B2B SaaS. Человеческая ошибка (забытый предикат `WHERE n.tenant_id = $id`) приводит к компрометации закрытой архитектуры клиентов.

## Последствия

### Плюсы
- Закрываются блокирующие вопросы OQ-2 и OQ-5.
- Единый технологический стек хранения (PostgreSQL 16) для метаданных платформы и графа связей.
- Жесткая физическая изоляция данных клиентов без накладных расходов на отдельные инстансы СУБД для каждого тенанта.
- Защита инвестиций в кодовую базу: сохранение Cypher-совместимости для будущего масштабирования.

### Минусы
- Необходимость управления схемами `tenant_<id>` в PostgreSQL при миграциях DDL.
- Ограничения Apache AGE при сложных многохоповых выборках (более 3–4 хопов), требующие кэширования типовых запросов в Redis.

### Риски
- Специфика синтаксиса openCypher в Apache AGE (например, оборачивание вызовов в SQL-функцию `cypher('graph_name', $$ ... $$) as (v agtype)`).
- *Митигация:* Изоляция диалекта в DAL-адаптере модуля `model`, обеспечение покрытия интеграционными тестами в рамках Docker-окружения (`ARCH-17`).
