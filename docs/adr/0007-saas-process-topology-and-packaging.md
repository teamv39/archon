# 0007. Физическая топология процессов SaaS и упаковка модулей

Дата: 2026-09-07

## Статус

Accepted (закрывает блокер OQ-8)

## Контекст

После принятия [ADR-0004](0004-module-decomposition-revision-1.md) (17 логических модулей) и перехода к облачной модели Managed SaaS в [ADR-0006](0006-saas-delivery-model-and-ai-native-source-of-truth.md) встал вопрос о физической топологии системы. 

Локальный all-in-one бинарник перестал быть целевой топологией. Развертывание 17 отдельных микросервисов для команды из 4 человек создало бы неприемлемые операционные накладные расходы. В то же время технологический стек разделен по языкам ([tech-stack.md](../architecture/tech-stack.md)):
- Ядро, графовая модель и детерминированные парсеры пишутся на **Kotlin / JVM** (Паша);
- Семантический анализ, промпт-пайплайны и интеграции с LLM пишутся на **Python** (Миша);
- Веб-портал разрабатывается на **TypeScript / React** (Фронтенд / пул).

Требовалось определить упаковку 17 модулей в 2–3 сборочные единицы, протоколы межпроцессного взаимодействия, гарантии Privacy-by-default для кода клиентов и закрыть архитектурный блокер **OQ-8**.

## Решение

Принята следующая физическая топология облачного сервиса Archon (детализирована в [deployment.md](../architecture/deployment.md)):

### 1. Упаковка в 3 сборочные единицы (Deployable Units)
1. **`archon-core-service` (Kotlin / JVM):**
   - Включает модули: `model`, `resolve`, `policies`, `drift` (синтаксический анализ), `assurance`, `export`, `registry`, `sources`, `extract` (AST и манифесты), `reconcile`, `platform`.
   - Предоставляет Public REST API, Webhook-контроллер для интеграций с GitHub/GitLab, управляет схемой PostgreSQL + Apache AGE.
   - Запускает координатор пайплайнов анализа (Temporal Workflow & Core Activities).
2. **`archon-ai-service` (Python 3.11+):**
   - Включает модули: `interpret` (File Selector + Architecture Extractor), `drift` (семантический дрейф документации), компоненты RAG.
   - Выступает воркером Temporal (AI Activity Worker), обрабатывающим задачи семантического извлечения фактов через внешние LLM-провайдеры и векторную БД Qdrant.
   - В рамках MVP хостит исследовательский FastMCP сервер для Cursor IDE.
3. **`archon-portal` (TypeScript / React / Vite):**
   - Статическое SPA-приложение, обслуживаемое через Nginx: интерактивный просмотрщик LikeC4 диаграмм, каталог микросервисов, инбокс находок и решений.

### 2. Оркестрация через Temporal Polyglot Workflows
Связка этапов анализа репозитория организуется через оркестратор **Temporal**:
- Пайплайн оформляется как единый `RepoIngestionWorkflow` в Kotlin.
- Шаг 1 (Клонирование в память + AST-парсер) выполняется Kotlin-воркером (`archon-core-service`).
- Шаг 2 (Семантическое извлечение и валидация фактов через LLM) выполняется Python-воркером (`archon-ai-service`).
- Шаг 3 (Примирение `reconcile` и запись в Apache AGE) выполняется Kotlin-воркером (`archon-core-service`).
- Воркеры работают по pull-модели (вычитывание задач из брокера), что исключает необходимость прямого синхронного HTTP-сопряжения и открытых внутренних портов.

### 3. Гарантии изоляции и Privacy-by-default
- Исходный код репозиториев клиентов клонируется во временный RAM-диск (`emptyDir: { medium: "Memory" }` в K8s pod) с глубиной `--depth=1`.
- Сразу после синтаксического разбора код принудительно удаляется (`rm -rf`).
- В долговременное хранилище (PostgreSQL + Apache AGE) сохраняются исключительно архитектурные факты, сигнатуры API и диапазоны строк `evidence_files` (3–5 строк цитаты кода для подтверждения истинности).

### 4. Сетевой контур
- Для MVP не разворачивается отдельный тяжелый кластер API Gateway.
- Используется стандартный Ingress-контроллер (Nginx):
  - `/` — раздача статики `archon-portal`;
  - `/api/*` — проксирование в `archon-core-service`;
  - `/mcp/*` — проксирование в `archon-ai-service` (FastMCP).

## Альтернативы

### Вариант 1: Монолитный Ingestion Worker (Polyglot JVM + Python образ)
Попытка объединить `extract` и `interpret` в один контейнер с установленными JVM и Python-рантаймом.

**Плюсы:**
- Меньше отдельных сервисов.

**Минусы:**
- Огромный размер базового Docker-образа (2GB+).
- Конфликт зависимостей и версий библиотек.
- Затрудняет параллельную локальную разработку Паши (Kotlin) и Миши (Python).

**Почему не выбрали:** Нарушает принцип автономности разработки модулей и чистоты стека.

### Вариант 2: Микросервисная топология (17 сервисов по числу модулей)
Развертывание каждого из 17 модулей фабрики как отдельного сервиса.

**Плюсы:**
- Абсолютная независимость компонентов.

**Минусы:**
- Колоссальные операционные затраты для команды из 4 человек.
- Высокие задержки на сетевую сериализацию графовых данных.
- Прямое нарушение договоренности из ADR-0004: "17 модулей — логика, не сервисы".

**Почему не выбрали:** Избыточное усложнение на этапе MVP.

### Вариант 3: Синхронный REST/gRPC между Core и AI без Temporal
Прямой вызов Python-сервиса из Kotlin-ядра по HTTP/gRPC.

**Плюсы:**
- Не требуется развертывать кластер Temporal на старте.

**Минусы:**
- Длительные вызовы к LLM (30–60 секунд) требуют ручной реализации очередей, стейт-машин в БД, обработки таймаутов и экспоненциального бэкоффа при 429 ошибках провайдеров.
- При падении сервиса в процессе разбора теряется состояние всего пайплайна.

**Почему не выбрали:** Temporal дает надежные саги, ретраи отдельных активностей без перепарсинга AST и мониторинг из коробки.

## Последствия

### Плюсы
- Четкое разделение зон ответственности инженеров (Паша — Core/AGE, Миша — AI/LLM).
- Надежная оркестрация распределенного конвейера анализа через Temporal.
- Выполнение требований корпоративной безопасности (код не сохраняется на диск).
- Полное закрытие архитектурного блокера OQ-8.

### Минусы
- Необходимость поддержки локального Temporal Server в Docker Compose (задача #30).
- Необходимость координации DTO-контракта между Kotlin и Python активностями (Extraction Contract v1.0, задача #34).

### Риски
- **Сложность Temporal для команды:** Java/Kotlin и Python SDK Temporal требуют понимания детерминизма воркфлоу.
  - *Митигация:* Использовать простейшие линейные воркфлоу, вынося всю бизнес-логику в активности (Activities).
- **Развитие MCP:** FastMCP на Python может не обеспечить требуемую производительность при высоких нагрузках.
  - *Митигация:* В MVP FastMCP валидирует сценарии работы с Cursor; при масштабировании MCP-интерфейс будет перенесен в `archon-core-service`.
