# ТЗ на дизайн: Паспорт сервиса (Service Passport)

* **Роут:** `/services/:id`
* **Роль в продукте:** Детальное инженерное досье микросервиса. Не является отдельной базой знаний и не дублирует данные, а проецирует граф `model` и вердикты `assurance`.
* **Исполнители:** Екатерина (Figma), Кирилл (React/Tailwind/`@xyflow/react`), Артем (BFF эндпоинты `/api/services/:id`).

---

## 1. Задачи пользователя (JTBD)

1. **Разработчик-интегратор:** быстро понять контракт сервиса (какие эндпоинты есть, какие DTO принимаются) и скопировать проверенный контекст для своего AI-агента в Cursor.
2. **Архитектор:** исследовать топологию сервиса (кто вызывает его, кого вызывает он, какие БД используются) на локальном интерактивном графе (xyflow).
3. **Тимлид сервиса:** проверить наличие активных расхождений документации и кода, относящихся к его сервису.

## 3. Шапка паспорта (Hero Banner)

* **Хлебные крошки:** `Каталог сервисов / billing-service` (ссылка назад на `/services`).
* **Заголовок и статус:**
  * Название сервиса крупным моноширинным шрифтом (`text-2xl font-bold`).
  * Бейдж критичности: `Tier-1` (Mission Critical).
  * Бейдж статуса дрейфа: `In Sync` (зеленый) или `Drift Detected (2)` (красный, кликабельный).
* **Мета-блок:**
  * Команда-владелец: ссылка на команду `@payments-team`.
  * Ссылки на внешние ресурсы: иконка Git-репозитория (`GitHub: teamv39/billing`), ссылка на Swagger/OpenAPI (если есть), ссылка на исходный файл архитектурного описания в репо.
  * Индикатор синхронизации: `Синхронизировано 12м назад (коммит a4f109c)`.
* **Кнопка быстрого действия:**
  * **«Скопировать MCP-контекст» (Copy Context for AI):** копирует в буфер нормализованный JSON-манифест сервиса для AI-ассистентов в IDE.

## 4. Спецификация вкладок

### 4.1. Вкладка 1: Обзор (Overview)
Базовая сводка и оперативный статус сервиса:
* **Текстовое описание:** блок описания из `README.md` или манифеста репозитория.
* **Карточки ключевых метрик:**
  * Количество API эндпоинтов (например, `14 эндпоинтов`);
  * Число входящих потребителей (`3 сервиса`);
  * Число исходящих зависимостей (`5 сервисов, 2 базы данных`);
  * Дата первого появления в графе.
* **Секция «Активные расхождения (Drift & Assurance)»:**
  * Если по сервису есть активный дрейф — выводится компактный список находок с бейджами критичности и ссылкой «Перейти к разбору в Инбокс».
  * Если дрейфа нет — выводится позитивный бейдж «Документация сервиса полностью соответствует коду».

---

### 4.2. Вкладка 2: Зависимости и топология (Dependencies)
Рабочее пространство для исследования связей:
* **Верхний блок: Локальный интерактивный C4-виджет (xyflow):**
  * Встроенный подграф на `@xyflow/react` (режим «1-hop окружение сервиса», фиксированный размер), сфокусированный строго на текущем сервисе.
  * Текущий сервис расположен по центру.
  * Входящие клиенты расположены слева (стрелки внутрь).
  * Исходящие зависимости и внешние сервисы расположены справа.
  * Базы данных (PostgreSQL, Redis) и очереди сообщений (Kafka) расположены снизу.
  * Клик по любому связанному сервису на графе открывает переход в его паспорт.
* **Нижний блок: Таблицы структурированных зависимостей:**
  * *Входящие вызовы:* Сервис-потребитель, протокол (HTTP REST / gRPC), вызываемый эндпоинт.
  * *Исходящие зависимости:* Целевой сервис, протокол, частота/назначение вызова.
  * *Ресурсы хранения и очередей:* База данных (имя БД, схема, тип), топики Kafka (pub/sub).

---

### 4.3. Вкладка 3: Контракты API (API Contracts)
Реестр извлеченных AST-анализатором интерфейсов:
* **Список методов сервиса:**
  * Компактный список эндпоинтов с цветными бейджами методов: `GET` (зеленый/синий), `POST` (желтый/синий), `PUT`, `DELETE`.
  * Путь роута моноширинным шрифтом: `/api/v1/payments/charge`.
* **Раскрывающаяся карточка метода (Accordion):**
  * Описание назначения метода (если извлечено из Javadoc/Docstring или документации).
  * Параметры запроса (Query, Headers, Body DTO).
  * Структура ответа (HTTP 200 DTO, возможные ошибки).
  * Координаты в кодовой базе: кликабельная ссылка на файл и строку объявления контроллера в коде (например, `src/controllers/ChargeController.kt#L45`).

## 5. Состояния экрана (States)

1. **Loading State:** Скелетон шапки и скелетон активной вкладки (`shadcn/skeleton`).
2. **Not Found State (404):** Если сервис удален или переименован: «Сервис не найден в графе знаний платформы. [Вернуться в каталог]».
3. **Empty Contracts State:** Если AST-парсер не нашел публичных эндпоинтов (например, фоновый worker или consumer очереди): информационный баннер «Сервис не экспортирует публичных HTTP-контрактов (фоновый обработчик)».
