# AGENTS.md — инструкция для агентных моделей

Этот файл — вход для любой LLM, работающей с репозиторием Archon.
Прочитай его первым, прежде чем трогать код или доки.

## Что такое Archon

Archon — enterprise-платформа docs-as-code и AI-native Source of Truth (Managed SaaS). Миссия — **Zero Drift**:
документация не расходится с кодом, а AI-агенты и инженеры получают проверенную архитектуру.

Интерфейсы взаимодействия: 4 ключевых канала — **MCP-сервер** (для IDE AI-агентов), **веб-портал** (для людей), **Git Sync / PR-бот** (двусторонняя синхронизация доков и гейты), **Public API** (для CI/CD и скриптов) + вспомогательный **чат-бот**. Внутри — 17 логических модулей (фабрика), включая генератор артефактов `export`. Подробно —
`docs/architecture/product-overview.md`.

## Ключевые договорённости

- **17 модулей — логика, не сервисы.** MVP собирается из 3 сборочных
  единиц (`archon-core-service`, `archon-ai-service`, `archon-portal`) по ADR-0007. Модуль != сервис.
- **Людей к модулям не привязываем** (ADR-0004, решение 4). В модуле
  поле "Компетенция" опционально, владельца нет.
- **Продуктовый срез (5 блоков)** и **технический срез (7 слоёв)** —
  два взгляда на одни и те же 17 модулей. Для рассказа — блоками.
- **Блокеры для кода сняты:** OQ-1 закрыт ADR-0002, OQ-2 и OQ-5 закрыты ADR-0003, OQ-8 закрыт ADR-0007. Топология и хранилище согласованы.
- **Декомпозиция принята** (ADR-0004, аддендумы ADR-0006, ADR-0007). Не перепридумывай модули без ADR.

## Как работать

1. Прочитай `AGENTS.md` (этот файл) и `docs/INDEX.md`.
2. Найди задачу в GitHub Issues/Projects или уточни у пользователя.
   - Готовые к работе задачи команды:
     ```bash
     python3 scripts/tasks.py --ready
     ```
   - Задачи конкретного человека (фильтр по имени или логину):
     ```bash
     python3 scripts/tasks.py --assignee денис   # или паша, миша, макс, артем
     ```
   - Доска портала (`archon-portal`, Project #3): добавь `--portal`.
   - Прямой вызов через GitHub CLI:
     ```bash
     gh project item-list 2 --owner teamv39 --format json
     gh issue list --state open --limit 30
     ```
3. Перед правкой — прочитай затрагиваемые файлы (Read, не угадывай).
4. Обсуди подход с пользователем до реализации (см. "Обсуждение решений").
5. Работай в ветке `feature/<id>-kebab` от `dev`.
6. Правь доки и код в одном PR/коммите, если меняешь поведение.
7. Архитектурные решения — только через ADR (`docs/adr/TEMPLATE.md`).
   Споры — в `open-questions.md`, не в файлах модулей.
8. Один модуль = один файл в `docs/architecture/modules/` по
   `TEMPLATE.md`. Модуль без строки в `modules/README.md` не существует.
9. Перед мержем — запроси ревью у пользователя (см. "Git").

## Обсуждение решений

Решения принимает пользователь, агент предлагает и аргументирует.

- Обсуждай до кода: выбор подхода, библиотеки, структуры, контракта,
  изменение скоупа, всё, что трогает ADR/OQ или архитектуру.
- Если доступен скилл `grill-me` — используй его для разбора плана.
  Если нет — задавай вопросы по одному, к каждому давай свою
  рекомендацию и варианты.
- Не выдавай предположение за согласованное решение. Итог обсуждения
  фиксируй в issue, ADR или `open-questions.md`.
- Мелочи (опечатки, форматирование, очевидные правки в рамках
  задачи) делай без обсуждения.

## Стиль

- Язык доков — русский, стиль — коротко и по-человечески.
- Без эмодзи, без пафоса, без декоративного юникода.
- Диаграммы — `mermaid` (flowchart). ASCII-бокс только для деревьев
  директорий. Проверяй рендер.
- Проверяй отсутствие CJK-артефактов после правки на русском
  (`python3 scripts/validate_docs.py --check-cjk`).
- Сохраняй бренды в цитатах/коде/путях как есть.

## Git

- `dev` — основная рабочая ветка. `main` — стабильная, обновляется
  только из `dev`.
- Ветки: `feature/<id>-kebab` от `dev`, мерж обратно в `dev`.
- **Агент не пушит в `main` и `dev` напрямую.** Только в свою
  feature-ветку.
- **Перед мержем в `dev` или `main` агент запрашивает ревью у
  пользователя:** показывает `git diff --stat`, краткое описание
  изменений и результат валидации, затем ждёт явного "ок". Молчание
  или "посмотрю позже" — не аппрув.
- Мерж `dev` → `main` — только по явной команде пользователя.
- Коммиты: `ARCH-123: что сделано` или краткий префикс типа
  `Docs:` / `Research:` / `Architecture:` если вне трекера.
- Перед пушем: `git status`, `git diff --stat`, проверка валидации доков (`python3 scripts/validate_docs.py --all`).

## Что не делать

- Не пушь в `main`/`dev` и не мержи без ревью пользователя.
- Не заводи `develop`/`module/*` и прочие долгоживущие ветки без просьбы.
- Не назначай задачу на двоих (один assignee, второй — reviewer).
- Не храни решения в чате — если нет в GitHub/docs, этого нет.
- Не расширяй скоуп молча. Нашёл проблему шире задачи — скажи одной
  фразой, продолжай в рамках скоупа.
- Не генерируй код без опоры на принятые ADR.

## Чек-лист перед мержем

- [ ] Работа в `feature/<id>-kebab`, цель мержа — `dev`
- [ ] Дока обновлена вместе с кодом (если менялась архитектура — ADR/OQ)
- [ ] Ссылки в `docs/INDEX.md` и `docs/research/README.md` обновлены (если новый док)
- [ ] Валидация пройдена (`python3 scripts/validate_docs.py --all`): Mermaid рендерится, CJK-артефактов нет, локальные ссылки валидны
- [ ] Коммит маленький, сообщение понятное
- [ ] Пользователь посмотрел изменения и явно разрешил мерж

## Если не знаешь, что делать

Спроси пользователя одним вопросом с вариантами и своей рекомендацией.
Безопасный дефолт без вопроса — только для мелочей в рамках задачи;
скажи, что предположил. Не блокируйся молча.
